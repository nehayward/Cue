# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Cue is a multi-platform SwiftUI music player that also controls Sonos speakers. It plays Apple Music, Plex, Subsonic, TuneIn, Audiobookshelf and local files on the device itself (`LocalPlaybackService`) and hands the same queue to a Sonos group (`PlaybackRoute`). It provides native apps for iOS, iPadOS, macOS and tvOS, and includes a menu bar app (Cue Mini). Widgets and Live Activities are switched off for now (see Platform-Specific Features).

## Product Priorities

1. **Best music player first.** Cue is a player that happens to be an excellent Sonos client, not a Sonos remote with a player bolted on. Playback, queue, library, search and Now Playing must be complete on the device alone, with no speaker on the network.
2. **Best Sonos client second.** Everything the device can play must also play on a Sonos group, and the hand-off between the two must be seamless (`PlaybackRoute`).
3. **Every service must play on the device and on Sonos.** A service belongs in Cue only if its audio can be played by the device (MusicKit, a direct stream URL, or a local file) *and* by a speaker. Services whose audio only a speaker can reach are not supported, however popular they are on Sonos. Today that rule excludes Spotify, Tidal, Deezer, SoundCloud, Pandora, Sonos Radio and the speaker's own Music Library. See `Ideas/device-first-services.md` for the audit and the removal plan.

When a change forces a trade-off between the player and the Sonos client, the player wins. Do not add a service, feature or screen that only works when a speaker is present.

## Session Workflow

These rules apply to every session on the Mac (started with `Scripts/claude-remote.sh` and driven from the phone).

### Branch per session
- At the start of every session, before editing anything, create a new branch from the latest `main`: `git fetch origin main && git switch -c claude/<short-topic> origin/main`. Name it after the task, for example `claude/queue-swipe-actions`. If the working tree has uncommitted changes, ask before switching.
- Make every change and commit of the session on that branch. Do not commit to `main`, and do not start another branch in the same session.
- Push the branch with `git push -u origin <branch>` when work is committed. Merge to `main` only when asked.

### Deploy to the iPhone after every build
- When you build the iOS app, run `Scripts/deploy-to-iphone.sh` instead of a simulator build. It builds the `Cue` scheme (Debug) for the connected iPhone, installs it and launches it. The user tests on the phone, so a change is not finished until it has been deployed.
- On failure, it prints the compile errors and writes the full log to `build/device-build.log`. Fix the errors and run it again.
- If it reports that no iPhone is connected, build for the simulator instead (`xcodebuild -project Cue.xcodeproj -scheme Cue -destination 'generic/platform=iOS Simulator' build`) and tell the user the phone was not reachable.
- The script also installs the watch app from the build straight onto the paired Apple Watch (`Scripts/list-watches.py` finds it; `CUE_WATCH=<name or UDID>` picks one, `--no-watch` skips it), so the watch's reason shows in the output when it refuses. The watch has to be known to Xcode (Devices and Simulators) with Developer Mode on.
- Other targets (Mac, TV, Cue Mini) build with `xcodebuild` as usual; only the iOS and watch apps are deployed.

### Logs and crashes from the iPhone
- To check runtime behaviour, deploy with `Scripts/deploy-to-iphone.sh --logs [seconds]` (default 30), or relaunch without rebuilding with `Scripts/iphone-logs.sh [seconds]`. Ask the user to reproduce on the phone while it captures. It shows the last 200 lines; the full capture is in `build/device-console.log`. Set `CUE_LOG_FILTER=<text>` to see only matching lines. `print` and `Logger` output both appear.
- When the user is away from the Mac (on cellular, in the car), run `Scripts/iphone-applog.sh [lines]` once the phone is back in reach. A Debug build keeps its own log in files in its container (`Cue/Debug/PhoneLogFile.swift`: every `dance.cue` message, AVFoundation's errors and the requests that failed inside Cue, written every 20 s, on leaving the foreground and right after a player error, a file a launch, five kept), and the script copies them to `build/phone-logs` with `devicectl`, no password and nothing to do on the phone. A whole device log takes `sudo log collect --device-udid <udid>`, which needs the user at the Mac. A request that fails at once with -1008 and never reaches the server can be a content blocker's URL filter on the phone (Wipr blocked one Plex file URL once).
- When the user says the app crashed, run `Scripts/iphone-crashes.sh` (`--count N` for more) before reading code. It pulls Cue's newest crash report into `build/crashes` and prints the exception, the crash message and the crashed thread with Cue's frames symbolicated. If it says the phone's build doesn't match the local one, deploy again and ask the user to reproduce the crash.
- For crashes in an extension, pass `--process Widgets` (or the extension's executable name).
- For what the car's Now Playing read (CarPlay on iOS 27 sticks to one of Cue's two Now Playing cards), reproduce in the car or Xcode's CarPlay Simulator with the phone on USB, then run `Scripts/carplay-nowplaying-log.sh [15m]`: it collects the phone's system log (`sudo log collect`) into `build/carplay-nowplaying` and shows `mediaremoted`'s lines for `CarPlayTemplateUIHost` and `RemotePlayerService` beside Cue's `localplayback`, `carplay` and `nowplaying` lines.

### Cue (Mac) on this Mac
- `Cue (Mac)` is a Mac Catalyst build of the iOS app (code paths use `targetEnvironment(macCatalyst)`; `os(macOS)` is false there). When working on it, run `Scripts/deploy-to-mac.sh` after building: it builds the scheme (Debug) into `~/Library/Developer/Xcode/DerivedData/Cue-Mac` (`Debug-maccatalyst`), quits any running Cue and launches the new build on this Mac through LaunchServices. Build errors go to `build/mac-build.log`.
- Console: `Scripts/deploy-to-mac.sh --logs [seconds]`, or relaunch without rebuilding with `Scripts/mac-logs.sh [seconds]` (`CUE_LOG_FILTER` works the same). The running app keeps writing to `build/mac-console.log` (a link to `~/Library/Logs/Cue-dev/mac-console.log`).
- Release: prefix any Mac script with `CUE_CONFIGURATION=Release`. A locally built Release has no App Store receipt, so it runs as the free tier.
- Crashes: `Scripts/mac-crashes.sh` (`--count N`, `--process "Cue Mini"`) reads `~/Library/Logs/DiagnosticReports` and symbolicates against the last Mac build.
- Memory: `Scripts/mac-profile.sh [seconds]` relaunches the last Mac build, samples its footprint and its GPU share (default 120 s, every 1 s) while the user reproduces the problem, then captures a memory graph and reports the peak, the biggest jumps with timestamps, leaks, the largest regions (vmmap) and the largest heap types, into `build/profiles/<time>/`. `--stacks` adds allocation call stacks (`MallocStackLogging`), `--attach` profiles the Cue already running, `--trace <template> [seconds]` records an Instruments trace. GPU memory (`footprint`'s "(graphics)" rows) is invisible to `vmmap`, `heap` and the memgraph: a spike in `gpu_mb` alone is offscreen rendering or animation (see Mac GPU cost under Key Patterns), not an allocation leak. Profile the Debug build; Release builds can't be inspected by `leaks`/`heap`. These scripts are Clic's, renamed.

## Architecture

### Core Package Structure
The app is built around several Swift packages in `/Packages`:

1. **SonosKit** - Core Sonos integration and device communication
   - `SonosService` - Main service class managing Sonos system state
   - `SonosAPI` - Network communication with Sonos devices
   - XML parsers for Sonos responses
   - Device discovery and monitoring

2. **MusicSearchKit** - Music service integrations (also linked into the watch app, which browses Plex and Subsonic with it). A dynamic framework: the iOS app gets it embedded through SonosKit, but the watch links it directly, so its target embeds it in its own Embed Frameworks phase
   - Apple Music, Spotify, Plex, Tidal, TuneIn, SoundCloud APIs (only Apple Music, Plex, Subsonic, TuneIn, Audiobookshelf and Files are offered, `MediaSearchService.supported`)
   - Audiobookshelf (`AudiobookshelfAPI`); with the audiobook models it's pure Foundation, so its tests run with `swift test` on Linux given stand-ins for `os` and `Security`
   - Authentication services for each platform
   - Search result parsing and models

3. **SubscriptionKit** - In-app purchase management
   - RevenueCat integration for subscriptions

4. **Defaults** - Centralized app settings and storage keys
   - `AppStorageKeys`, `CloudKeys`, `GroupStorageKeys`
   - Feature flags and preferences

5. **VibesDS** - Custom UI design system
   - Reusable SwiftUI components and styles
   - `sidewaysPan(...)`: a drag that only starts sideways (`SidewaysPan`, a `UIPanGestureRecognizer` through `UIGestureRecognizerRepresentable`). It fails at once on a vertical drag and every other pan waits for it, so a volume row in a list or a sheet never takes a scroll or a pull to dismiss (Play On's rows use it)
   - `VibeSlider` (shared with Clic, file for file, as are `SidewaysPan` and `SliderMath`) drags with `SidewaysPan` on iOS, except `immediateDrag` sliders, which begin on touch-down (`TouchDownDrag`) to beat a navigation stack's back swipe. `onLongPress` fires when the slider is held still for half a second, and a held touch then never starts an edit (Clic's volume sliders mute with it). The Mac and visionOS keep the SwiftUI drag. No value animation while a drag is under way, and every division by the range goes through `SliderMath`, so a radio position past a zero duration can't make an infinite fill

6. **WatchSync** - What the iPhone and the watch app share (pure Foundation, tested with `swift test`)
   - `WatchPicks`/`WatchPick` (what's chosen to be on the watch, by id, merged per pick; a pick of a kind or server a side doesn't know is left out, not failed), `WatchBookPlaces` (each book's place, merged per book, the one that moved last winning), `WatchCredentials` (the iPhone's sign-ins; Audiobookshelf's access token lent, never its refresh token), `WatchKeys`, `WatchDownloadQuality`, `WatchSyncMessage` (the application context each side sends, and the watch's request for fresh sign-ins)
   - `TransferRateMeter` and `RouteEstimator`, which tell the watch's own Wi‑Fi from the iPhone relay by speed
   - `WatchAllowance` (the free tier's share of downloads the iPhone gives the watch, and which picked songs it admits) and `WatchHeldDownloads` (what the watch holds against it)
   - `WatchWidgetState`, what the watch app leaves in the app group (`group.dance.cue`) for its widgets

### Main App Structure
- **CueApp.swift** - Main app entry point with shared services
- **Router.swift** - Navigation and routing system
- **Services/** - Core app services (ImageCache, Queue, PlayHistory)
- **Search/** - Search functionality across music services
- **Library/** - Music library browsing and management
- **Routing/** - App navigation and destination management
- **Debug/** - Debug tools: the log screens, the phone's own log (`PhoneLogFile`), the launch-argument audits (`AudiobookAudit`, `DownloadAudit`, `LyricsAudit`, all `#if DEBUG`), `ScrollStopLog` (always on in Debug, `dance.cue` `scroll`: a line for each scroll of a list marked `scrollStopLog(_:)` — Radio, Audiobooks, Browse — flagging a fling that `STOPPED EARLY` or a pan `DROPPED`, with what happened since the finger landed: main-thread stalls over 100 ms, UserDefaults changes, tab screen and `CueApp` bodies, the accessory re-hosted, insets, tab and network changes; the Search field losing focus is logged the same way) and `ScreenshotArtwork`: `-dance.cue.blurArtwork YES` blurs every cover, through Nuke's decoder, for App Store screenshots of a library that isn't ours to show (the watch app takes the same argument, `Watch/Debug/WatchScreenshotArtwork`, a box blur by hand since watchOS has no Core Image)

### Platform-Specific Apps
- **CueMini/** - macOS menu bar app for quick controls
- **TV/** - tvOS app optimized for Apple TV
- **CarPlay/** - the iPhone app's CarPlay scene (built by the Cue target only; there is no separate CarPlay target)
- **Watch/** - watchOS app (`Cue (Watch)`, embedded in the iOS app): plays Plex and Subsonic songs, and Plex and Audiobookshelf books, downloaded to the watch. See Apple Watch below

- **PlayAction/** - Share sheet extension for queuing music
- **Website/** - cue.dance, a Cloudflare Worker (see `Website/README.md`). Release pages and the in-app What's New JSON come from `Website/src/content/releases.js` (starting at 2026.1), and `/help` and `/releases/<version>` are opened by the app's web views

- `MusicSearchService.shared` - Music service search coordination

## Development Guidelines

### Code Organization
- Use `@Observable` for SwiftUI state management
- Services follow singleton pattern with `.shared` instances
- UI components are organized by feature area
- Packages are used for modular, reusable functionality

### Key Patterns
- **Router-based navigation** using `RouterDestination` enums
- **Service injection** through SwiftUI environment
- **CloudStorage** for synced user preferences
- **AppStorage** for local device settings
- **Super** (ported from Clic): `SubscriptionService.apply(_:)` settles it from RevenueCat's customer info (an active entitlement, an active subscription or any one-off purchase) or StoreKit's `Transaction.currentEntitlements` (`StoreKitEntitlements`, the one file that imports StoreKit); either is enough, and of two yeses the longer counts. StoreKit is there because each install's RevenueCat user is anonymous: a device that never restored reads as not subscribed though the account owns Super. RevenueCat is configured only once protected data is available (`whenProtectedDataIsAvailable`, not waited for on the Mac); `userID` reads empty until then. Each answer goes to `SuperPublisher` (set as `subscriptionUpdated` before `AppBootstrapper.bootstrap`), which writes `Subscription.activeUntil` to the App Group (`UserDefaults.superUntil`, `.distantPast` for no); `bootstrap` resumes from it (`resume(activeUntil:)`) so Super doesn't flash the free tier at launch, and the Shortcuts actions check `GroupStorageKeys.defaults.hasSuper` (this device's date, else the old iCloud flag only Debug and TestFlight builds wrote) and throw `IntentError.superRequired`, which says why. Never publish the launch default: `subscription` is `.notActive` until an answer comes. The paywall closes itself when `isActive` turns on, and `cue://subscribe` opens it only without Super. A gate's paywall (`FeatureGate.presentPaywall()`, `unlock`) goes up over whatever is on screen (`PaywallPresenter`, from the top view controller): a router's full-screen cover hangs off a tab's screen, which can't present over the player or a sheet, nor from a tab not showing, so Play On's locked rows opened nothing. Cue has a RevenueCat project of its own ("Cue": entitlement `cue_super`, offering `default` with `com.super.cue.monthly`, `com.super.cue.annual` and `com.cue.super.lifetime`); the Clic project's key, used before, offered Clic's products. The paywall's plans, Purchase, renewal terms, Restore Purchases and Terms/Privacy links are Cue's own (`PurchaseFooter`, buying through `Purchases.shared.purchase(package:)`), drawn from the current offering's packages with StoreKit's prices, the yearly plan's saving worked out against twelve months, and a free trial offered only when the Apple Account can still take it. A sale needs no app update: an introductory offer set up in App Store Connect (a free trial, a lower price paid up front for the first period, or a lower price for a few periods) shows on its plan, struck-through regular price and "% OFF" badge, on the button and in the terms; the RevenueCat offering's metadata can set `eyebrow` (the small line over the title, "Cue Super" otherwise), `headline` (the paywall's title), `badge` and `badge_plan` (`monthly`, `annual` or `lifetime`, chosen when the paywall opens; while it's set it's the only badge, and it shimmers). `Scripts/paywall-sale.py` shows and changes them from the terminal (`--badge "50% OFF" --plan monthly`, `--eyebrow`, `--headline`, `--clear`), with the secret key in `.secrets/revenuecat.env`; it changes the live offering, so every copy of Cue sees it. A Debug build launched with `-dance.cue.paywallSalePreview YES` shows a made-up sale (`PaywallSalePreview`) to look at. RevenueCat's footer needed an old-style template paywall on the offering and drew its default paywall over the table without one; it also closed the whole presentation when its load failed. A failed load leaves the paywall up with Try Again. In the app, ask `FeatureGate` (a `GatedFeature`'s `requirement`, or `hasSuper` for Super itself), never `subscription.isActive`, so a requirement changed in one place and the debug free tier reach every check. A Debug build on a device has Super (its receipt reads as TestFlight's), so to see the free tier there turn on Settings ▸ Debug ▸ Feature Gates ▸ Act as Free Tier (`FeatureGate.actsAsFreeTier`, also `-dance.cue.actsAsFreeTier YES` at launch or the `Cue [Free]` scheme); the Shortcuts actions still read the App Group's answer. Tests: `SubscriptionTests` (on an iOS Simulator destination, since SubscriptionKit imports UIKit)
- **One player for both routes**: the player, the mini player and the queue panel draw `PlaybackRoute.presented`, a `PlaybackController` (`Cue/Services/PlaybackController.swift`: `LocalPlaybackService` for this device, `SonosGroupController` for a group, times in seconds on both), not a branch on `route.group`. A route switch changes what the one set of views reads; while a hand-off carries the queue across, `presented` holds on the source (`PlaybackRoute.hold`) until the target is playing the same song with its cover cached, so the player never drops to the speaker's old track mid-switch. Held, `presented` is a `HeldPlaybackController`: the source's song, the hold's playing state and clock (the hand-off keeps it on what's heard through `setHoldClock`), and no commands (`isActive` false, transport no-ops), so views draw a hand-off without special cases; only the queue panel and the player's menus check `route.isHolding` to rest. The hold ends 12 s after the source stops, 30 s at most, and the hand-off's own calls on it are no-ops once a newer switch has cancelled it. The hardware volume follows `route.audibleGroup` (the source until it stops). Speaker-only extras (TV mode, its artwork badges and menu, room volume) read `controller.group`. Queue and drops go to `PlaybackRoute.controller` / `route.group` (the route itself). Song lists mark the song the player shows through `PlaybackRoute.isPresenting(_:)` (the speaker's track, or this device's station, else its queue's row), read in a small view of its own (`NowPlayingTitle`) so a new song redraws titles, not whole rows. Don't branch a player surface's whole body on the group: a view in two `if` branches is rebuilt on every switch
- **Radio on the device** plays in front of the queue, not in it: `LocalPlaybackService.station` holds the station and `nowPlaying` reads it first, while the queue keeps its songs, its place and the spot in its song (`resumePosition`) behind it, the way a speaker's queue waits while it plays radio. Next Up shows that queue dimmed under "Not Active" with no current row (CarPlay's Up Next says "Not Playing"), and a row tapped or any new Play puts the station away (`arm(at:)`). Stations never become queue rows (`queueable`); a station played at any position plays now (`playStation(_:)`), with `runEnd` at -1 so nothing that edits or tops up the queue reaches its player. It's saved on its own (`LocalStation.json`) and queue positions saved under it are the queue's spot, not the station's time. A station that won't play falls back to what was there (the station before it, or the queue, paused). A live Apple Music station (`.liveRadio`) has no Next; a personal one keeps it (`isPlayingAppleStation`), and Next on one that's stopped starts it
- **Queue editing**: Next Up (`QueueNextUpView`, the player's queue panel or sheet) edits the queue as Clic edits a speaker's, played rows included: a swipe or the context menu removes any row but the current track or plays it next, and Edit drags any row, the current one too (held in place with `moveDisabled`, it stood between the played rows and Up Next, and the song just before it couldn't be dragged after it). A row dropped above the current track counts as played, a played row sent to Play Next is heard again, and the current track dragged elsewhere plays on there, the rows it passed changing sides. On this device every edit goes through `LocalPlaybackService.rearrangeQueue`, which carries each stored queue index (the current track, `runEnd`, the Apple and stream runs' entries, the skip hold) to its row's new place, and cuts the armed run after the current track when Up Next changes. The Apple player's played entries keep their rows only while the played rows keep their order (else -1), so `previous()` steps back inside the player only to a row still behind the current one, and Next finds the entry after the current one (`appleEntry(after:)`), not the first row past it. Edits wait while an arm is under way (`armingIndex`). On a group the edit shows at once, goes to the speaker (`reorderQueue`, `removeTrackFromQueue`; positions from 1, `InsertBefore` counting the queue as it was, as `onMove` does) and the queue is read back. The book/music switch isn't in the queue: Back to Music and Back to Book are in the player's menu and at the top of each music library
- **Menu bar Playlist menu** (iPad and the Mac; `AppDelegate.buildMenu`, `PlaylistMenuCommands`): Add to Last Playlist and Add to Playlist act on the song the player shows (`PlaybackRoute.presented`; on this device the song on air for a station), never a station or a book's file. Add to Last Playlist is always a key command, named for the playlist by `LastPlaylist.save`'s menu rebuild, and built on or off by whether the song playing can go in it (`LastPlaylist.accepts`, the player's menu's rule too), the menu rebuilt when that turns (`followAddToLastPlaylist`, observing from launch): SwiftUI's app delegate stands in the responder chain in place of Cue's, so `AppDelegate.canPerformAction` is never asked (Undo and Redo, which rely on it, read as on). New Playlist makes one on the provider Browse shows, else the song's service, else the first switched on (never Sonos), asking for its name in an alert from the top controller (`NewPlaylistView.create` does the rest): `Router.main`'s sheet has no host in the window, each tab presenting from a router of its own, and `NewPlaylistView` presented from UIKit ignores its own sheet modifiers. Toasts on iPad and the Mac are drawn at the window (`withAlert(enabled: !isPhone)` on the `TabView`), since the tab screens draw them only on the phone. A toast that opens a playlist or collection when tapped does it through `MediaDetailPresenter` (a page sheet from the top controller, `TopViewController.current`), never `Router.main.presentedSheet`: nothing presents that, and a value left in it makes `addDismiss` draw its close button on screens that weren't presented
- **Apple → stream with the phone locked**: MusicKit plays in its own process, so with the phone locked iOS suspends Cue and nothing started the Plex, Subsonic or Files song after an Apple run. While an Apple run plays with a stream song next, `LocalPlaybackService.syncKeepAwake` holds `KeepAwakeAudio` (silence, `.mixWithOthers`, in `SilentAudioSession.swift`), taken on the poll while Cue still runs, kept through a pause of up to 10 minutes, and given up once the stream player is heard (`timeControlStatus == .playing`, on the stream poll) or when the next song isn't a stream. Not as the stream is told to play: while the song loads nothing is heard, iOS suspended Cue in that moment, and the song never started (its bytes come through Cue's own `CachingStreamLoader`). Logged as `keep-awake audio: held/released` under `nowplaying`. Silent audio to stay running is an App Review risk (guideline 2.5.4); it's scoped to this one case for that reason
- **AirPlay** (the stream player): AirPlay 2 through the `.longFormAudio` route sharing policy, set with `.playback` as each run or station starts (`LocalPlaybackService.setPlaybackCategory`, not on the Mac), since the session's other users (the Sonos mirror, `KeepAwakeAudio`, previews) set the default policy; it plays to the speakers chosen for Music and Podcasts, several at once. Its players have external playback off (`streamPlayer`'s `didSet`), so a receiver is never handed a cached song's `cue-stream:` URL, which only answers inside Cue. A speaker that shows as chosen and plays nothing in every app wants a power cycle, not code
- **Playback progress** is a running clock, not a ticking number: `Room.estimatedPlaybackPosition()` for a speaker, `LocalPlaybackService.progress` for this device. Draw it through VibesDS's `PlaybackTimeline` (redraws once per pixel, only while visible and playing), report positions through `Room.updatePlaybackPosition(_:)` / `noteProgress(_:)` rather than writing them, and move a speaker's position only through `SonosService.seek` / `next` / `previous`, which hold the bar until the speaker lands. Skips are instant and coalesced (`SonosService+TrackSkip.swift`). See `Docs/PlaybackProgress.md`
- **Lyrics**: `LyricsService.shared` (`Cue/Services/LyricsService.swift`) looks up the song `PlaybackRoute.presented` shows while the player is open (`LyricsRequestModifier`): the song's own service first (Plex lyric streams — asked for rendered with `format=xml`, since a bare request for a LyricFind stream is a 404 —, Subsonic `getLyricsBySongId`/`getLyrics`, a Files `.lrc`/`.txt` sidecar or tags), then LRCLIB (`LRCLibAPI`, behind Settings ▸ Playback ▸ Look Up Lyrics Online, off by default), cached in Caches/Lyrics. The model and parsers are in `MusicSearchKit/Lyrics` (`LyricsTests`). `LyricsView` follows the presented controller's clock; on iPhone lyrics are full screen (`PlayerView.phoneContent`, one layout for cover and lyrics so the cover itself shrinks into the header), elsewhere they take the cover's place. Don't start a lyrics glide alongside anything that resizes the lyrics (the full-screen controls coming back): the resize cuts the glide short. The line being sung fills every frame through a `TextRenderer` drawn over a hidden copy of the line; a renderer that changes every frame on a laid-out `Text` makes SwiftUI measure it and lay out (and scroll-track) everything around it each frame, which on an iPhone SE was two fifths of the main thread. - **Mac GPU cost**: on the Mac an animated SF Symbol swap or pulse, a `MeshGradient` whose colours change, or an animated swap of the whole player costs ~90 MB of GPU memory for ~2 s each time, and text redrawn through a `TextRenderer` costs the same for as long as it keeps changing, so those are off or replaced there (the lyrics' fill is a sliding mask, `LyricFill`; `GroupMediaControlsView.animatesPlayPause`, `PlaybackIconView`, `VibeGaugeView`) and the player backdrop is a small CPU-drawn bitmap (`ArtworkMeshBackground`)
- **Glass sheet text**: rows on the player's glass sheets (the Chapters sheet's chapters and history, `AudiobookChapterRowLabel`, `AudiobookHistoryList`) dim with opacities of `.primary` (0.8 for a time, 0.6 for a subtitle), not `.secondary` or `.tertiary`, whose vibrancy flickers while the sheet's glass transitions
- **UserDefaults writes**: any write to `UserDefaults.standard`, of any key, re-runs every view holding `@AppStorage` (`CueApp`, each tab's screen, many rows). Never write on a timer or a poll, and never write a value back unchanged: a mutating call on an `@AppStorage` value (`searchSelection.prune(...)`) saves it every time, even when nothing changed. Search's did, from a `.task` that the write itself brought back, ~35 times a second, and Radio's list, rebuilt with every write, wouldn't scroll or take taps on the phone. Change a copy and assign it only when it differs. The same goes for `@Observable` properties, which notify on every write, equal or not: what runs as Cue comes back to the foreground (`AppleDownloadsIndex`'s sweep), as a tab shows (Radio's Apple stations) or with each search (Plex's book library keys, `knownAudiobookLibraryKeys`, which were saved on every Plex search, and the search suggestions) writes only what changed. Don't make environment objects in a builder that `CueApp` re-runs (`Screens` keeps one `SelectedGroupService` per tab): a new one redraws every row that reads it. Keep `@AppStorage` out of rows and tab screens (read a setting when it's used, or observe a store): a view holding one re-runs on every write, iOS's own as Cue comes back included, and a tab screen holding one comes back as a new view on every `CueApp` pass, its navigation stack handing each row a new `dismiss` (`PlayableContentRowView` reads `dismiss` only through `DismissReader`). The selected tab is kept as Cue leaves the foreground (`Router.saveSelectedTab()`), not on each switch. Search's services are `SearchSelectionStore`, not `@AppStorage`, and `Router.path` drops writes that don't change it (a navigation stack writes its path back as the scene returns). To find a writer, launch a Debug build with `-dance.cue.logDefaultsWrites YES` (`DefaultsWriteLog`: writes by key every 2 s and who made each key's first, under `dance.cue` `defaults`)
- **Lazy stacks of sections**: a `LazyVStack` of a few mixed-height sections (Audiobooks' tab) estimates the ones out of view and corrects them as they come in, so the page's height changes mid-scroll and the scroll jolts or stops dead. Use a plain `VStack` for a page of sections (with `.frame(maxWidth: .infinity)`, which a lazy stack had by itself) and keep the laziness in the long rows and shelves inside them. A SwiftUI `ScrollView` tab page also re-lays itself out when the tab bar shrinks on scroll (the bottom safe area moving 56 pt), which stopped short pages mid-coast; Audiobooks ignores the bottom safe area and keeps the full bar's height as a fixed margin (`fullBottomInset`). `List` pages take the change in place. UIKit shrinks or grows the bar from inside the scroll view's own step (its scroll observers, `_notifyDidScroll`), laying out the bar, the mini player and the tab right there, 30 ms or more in the Simulator; Audiobooks' flicks on the iPhone stopped where it shrank (about 70 pt down), and that tab went without the shrink for a while, but the stops were the tabs handed over again (below), and every tab shrinks it
- **Tabs handed over again**: SwiftUI's `TabView` calls `setTabs(_:animated:)` with the same `UITab` objects on updates that change no tab (every `CueApp` pass, and on the iPhone each accessibility query for the focused element, several a second with an accessibility feature on), and UIKit then takes the selected tab's page out of the window and back: a text field there loses the keyboard and a scroll stops. `SameTabsFilter` (`Cue/Extensions/UITabBarController+SameTabs.swift`, installed first in `didFinishLaunching`) drops those; keep it, and don't hand UIKit tabs another way. The Simulator doesn't show it
- **AppState** (`Cue/AppState.swift`): what `CueApp`'s scene reads, observed: the Appearance settings (tab switches, theme), the queue panel's flag (`showsQueuePanel`, also the player's), and the tab rules (which tabs show, the fallback, the Downloads icon and badge). It's the one writer of those settings: Settings ▸ Appearance and Debug bind to it, and each property saves to UserDefaults when it changes, with nothing listening for other keys' writes. Keep `@AppStorage` and `@CloudStorage` out of `CueApp`: add a setting the scene reads here, and read one used only on an event (Quick Launch, onboarding) when it happens
- **Privacy manifests**: every bundle the iPhone app ships has its own `PrivacyInfo.xcprivacy`, since App Store Connect checks each binary: the root one (the app, shared with Mac, TV and Vision), `PlayAction/` (both share extensions, which link SonosKit and Defaults), `Watch/`, `WatchWidgets/`, and MusicSearchKit's (a package resource, as it's a dynamic framework). A new use of a required-reason API (UserDefaults, file timestamps such as `contentModificationDateKey` or `attributesOfItem`, disk space, boot time) needs its reason in the manifest of each bundle whose code makes the call

### Sonos Integration
- Sonos is opt-in in the iOS/Mac app: `SonosService.isEnabled` (asked in onboarding by `SonosQuestionStep`; changed later in Settings ▸ Sonos ▸ Use Sonos Speakers; while it is off the Play On button is the system AirPlay picker). While it is off, monitoring and group loads never touch the network, so no Local Network prompt appears. Speakers are only on the local network, so on cellular alone Cue acts as if Sonos were off. `SonosService.isAvailable` (Sonos on, Wi‑Fi or Ethernet, and not in a car) is the one switch: `SonosSystemDiscoverService` reads the path on the main queue and counts losing Wi‑Fi after 5 s (`cellularGrace`, so a moment's drop doesn't), at once on the first path or one read as Cue comes back to the foreground (it may have changed while Cue was suspended); `SonosService` then clears the groups, and looks for them again when Wi‑Fi is back. In a car (CarPlay's screen up or the sound going to CarPlay: `CarConnection`, started at launch and told by `CarPlaySceneDelegate`) `SonosService.isInCar` puts the groups away the same way, and `monitor()` and the group loads stay off the network even on Wi‑Fi, until the car is gone. The speaker stays chosen while away, so the route goes back to it on Wi‑Fi, unless this device played meanwhile: `LocalPlaybackService` calls `PlaybackRoute.deviceStartedPlaying()` whenever it starts, which makes This Device the choice while no speaker is in reach. - **CarPlay**: `CarPlay/` is an audio-app template scene (Home, Audiobooks, Downloads, Radio; an audio app gets four tabs at most) that always plays on the device and has no Sonos UI: a speaker has no place in a car. Home is Resume and Recently Played over the library; Audiobooks shows while a server has books (`CarPlayLibrary.showsAudiobooks`, put in and taken out with `updateTemplates`; unlike the phone's tab, never empty, since nothing can be signed in to from the car): the books partway through as rows with a progress bar, then each server's books as grids. A book plays through `AudiobookPlayer` from where it was left (`CarPlayPlayback.play(book:)`), and Now Playing gives it a `CPNowPlayingPlaybackRateButton` (`bookRates`) in place of shuffle and repeat, and, for a book with chapters, the chapter's place in the book in place of the queue button. It opens Chapters (`fillChapters`): the chapter playing and the ones to come, not those heard (a car can't open a list partway down), each played from its start with `AudiobookPlayer.play(chapter:)`; the one playing has a bar and its time left, set on its row as the book plays (`showChapterProgress`). While CarPlay is connected the phone's app drops Sonos too (`SonosService.isInCar`, see Sonos Integration). Apple Music in the car is left to iOS. MusicKit's player publishes its own Now Playing client from a process of its own, and on iOS 27 the car's Now Playing screen stays on whichever of the app's two clients (Cue's own, MusicKit's) it was on rather than following the one making sound, so during Apple Music it can show a stale or blank card, or a play button while the music plays (FB24840951; https://developer.apple.com/forums/thread/847151). That's Apple's bug and Cue doesn't work around it: publishing Apple Music on Cue's own card and restating it, playing silence to keep Cue awake beside MusicKit, and a paused card for a queue with nothing in a player were all tried and taken out as hacks. (Silence beside MusicKit is back for one other case only, an Apple run with a stream song next, so that song starts with the phone locked: `KeepAwakeAudio`, see Key Patterns.) The two cards are two MediaRemote clients: Cue's process (`dance.cue(<pid>) > default`) and MusicKit's player in `com.apple.MediaPlayer.RemotePlayerService`. It goes the other way too: a book started after an Apple Music song showed the song, paused, in the car while the book played. So when the stream player takes over from Apple Music, Cue empties MusicKit's stopped queue (`LocalPlaybackService.releaseAppleQueue`), leaving its card nothing stale to show. Between two stream runs (a book to Plex, a book's next file, a song again under Repeat One) Cue's card stays up with its commands while the next run loads (`teardownRun(keepingCard:)`, `finishRun`) and comes down only when nothing plays after: cleared and stopped in between, with its commands gone, the car's Now Playing could let go of it and stay blank for the next song. `LocalNowPlayingPresenter` logs `card up:`, `card kept` and `card down` under `nowplaying`. Under test: iOS 27's MiniPlayer is off in Debug builds (`allowsMiniPlayer`, the template having been reworked with it; release builds keep it), with Settings ▸ Debug ▸ CarPlay MiniPlayer to turn it back on from the next connection, and `Scripts/carplay-nowplaying-log.sh` collects the phone's log (sudo) and shows which card `CarPlayTemplateUIHost` read beside Cue's hand-offs. Next lever if neither moves it: the stream player's card through an `MPNowPlayingSession` (its `AVQueuePlayer`, `becomeActiveIfPossible`). A TuneIn station's card is live (`MPNowPlayingInfoPropertyIsLiveStream`, `update(isLive:)`): the LIVE bar, the station's name on the album line, and play/pause only. iOS draws a live card's pause as a stop button whatever the app does, so `stopCommand` pauses, and skips, scrubbing, shuffle and repeat are switched off, which greys out what can't be hidden; each live publish logs `live card:` under the `nowplaying` category. Apple's reasoning (DTS): a live stream can't be resumed, only rejoined, so a TuneIn station paused for over 30 s (`liveResumeLimit`) starts again live on Play rather than resuming a stream its server has likely dropped. Command states are set only when they change, ahead of the card, and Now Playing's buttons are only sent to the car when they change (`nowPlayingButtons`). Buttons above a list are tiles (`tileRow`: an image row of condensed elements, symbol beside title on a platter, like the Music app's Library buttons), not `headerGridButtons`, which have no platter and on iOS 27 draw only a plain `UIImage(systemName:)` (FB24806621). Home's tiles are a switch: a section (Playlists, Recently Added, Albums) fills the list under them in place. Home's sections (a grid per provider) and Radio are image grids (`imageGrid`: squares with names, 12 at most, the title opening the rest as rows; the playing station's accessory symbol is set by `updatePlayingIndicators`). Rows use `CarPlayArtwork.symbol` and tiles `CarPlayArtwork.tile` so they aren't black on the car's dark screen. Now Playing's shuffle and repeat buttons only take a tap while `changeShuffleModeCommand` / `changeRepeatModeCommand` are enabled with a target (`LocalNowPlayingPresenter` registers them for a stream run, `CarPlayInterface.registerModeCommands` its own while the car is connected so they work during Apple Music too, and the Sonos mirror switches them off for its own card), and the queue button is Cue's own: the system's Up Next button only takes a word or the car's icon, so it's off and a `CPNowPlayingImageButton` shows the song's place in a circle (`CarPlayArtwork.placeButton`: the plain `N.circle` symbol, a list past 50; the phone's ring drawn as a bitmap came out a dot on iOS 27), at zero under a station, which leaves the queue waiting, and opens Up Next. The entitlement is in `Cue/Cue-iOS.entitlements` (iOS SDKs only; `Cue.entitlements` is shared with Mac/TV/Vision and must not carry it), the scene is in `Cue/Info.plist`, and `AppDelegate.application(_:configurationForConnecting:)` hands that role `CarPlaySceneDelegate`. - **watchOS**: A device-first player for Plex and Subsonic, rewritten from scratch (the old Sonos remote and its widgets live in git history). The watch is the client: it browses and searches the servers itself with MusicSearchKit (its home screen, `WatchLibraryBrowser`, `WatchAccounts`), with the sign-ins the iPhone shares (`WatchCredentials`). What's on the watch is a list of picks — albums, playlists, artists and songs by id (`WatchPicks`) — made on either device: browsing on the watch, Add to Apple Watch in a menu on the iPhone (Settings ▸ Apple Watch lists them). Only the picks cross, as each side's application context (the iPhone's also carries the sign-ins); each side merges what arrives per pick (later of add and removal wins, removals kept as tombstones) and sends back only when the other was missing something. The watch looks each pick up on its server (`WatchLibraryBrowser.songs(for:)`), again when the sign-ins change and every six hours, and `WatchDownloadStore` downloads the songs; `WatchPlayer` plays the files through a long-form audio session (`UIBackgroundModes: audio` — watchOS ignores `WKBackgroundModes` for audio). **Books** are picks too (`WatchPick.Kind.audiobook`: a Plex album in a library kept for books, the iPhone's choice of libraries crossing with the Plex sign-in, or an Audiobookshelf item), added from the watch's Audiobooks shelves (Continue Listening, Plex Books, Audiobookshelf; `WatchBookShelf`, `BrowseBookScreen`) or Add to Apple Watch in a book's menu and page on the iPhone. `WatchLibraryBrowser.book(for:)` reads a book's files, chapters (Plex's marks, Audiobookshelf's, else the downloaded files' own with AVFoundation, `readChaptersIfNeeded`) and the server's place; its files come down as the server keeps them, whatever the quality, and stay out of the music (counts, Shuffle Downloads). `WatchPlayer.playBook` plays one from its place (`WatchBookStore`), at its own speed, with ±15/30 s skips for Previous/Next, keeps the place every 5 s and on a pause, and stops at a file not downloaded yet rather than skip it; `BookScreen` is its page. Now Playing shows a book as Apple Books does: the chapter over the book's title, the time into the chapter against its length, and the chapter number, moved on the moment the next chapter starts (a boundary time observer at its start in the file playing). The app's Now Playing (`NowPlayingScreen`) is Cue's own, the same face as the iPhone's player (`PlayerFace`): a book's chapter over the book (the song over the artist), the transport large, a thin line of how far into the chapter with the time left beside it, the transport as glass circles that click (`glassCircle(side:)`: sized by hand, as the glass button style pads its label to its own size), the sleep timer and a book's speed bottom left (`PlayerOptionsSheet`), where it plays in the middle — a tap opens Play On (`PlayOnSheet`: Apple Watch, the iPhone and each Sonos group it may play to, `WatchSyncMessage.routesRequest`; a book or the album the song playing is from moves to the choice, and the iPhone's playback moves between its routes, `switchRouteRequest`, or a book on the watch comes here) — and the volume on the Digital Crown (`VolumeControl`, `WKInterfaceVolumeControl` through `WKInterfaceObjectRepresentable`: `.local` here, `.companion` on the iPhone's player), with a button top right to the book's page while a book plays. The bottom row is the face's own, not a `.bottomBar` toolbar, which went missing after swiping back from a screen pushed over the player. The playing chapter's row is filled as far as it's been heard (`ChapterRowFill`), here and on the iPhone's chapters. Not the system's `NowPlayingView`, which picks its source itself: with the iPhone playing it showed the iPhone's under the watch's card. watchOS gives apps no route picker, so the output is the system's call (the headphones connected, else its picker as playing starts); the player's glyph turns into the headphones it plays to (`WatchPlayer.output`, from the audio session's route), and Play On's Headphones & Speakers opens the system's `NowPlayingView` for its output button. Places cross with the picks, and through iCloud's key-value store for when the two are out of reach (`CloudBookPlaces`: both apps name the iPhone app's store, `$(TeamIdentifierPrefix)$(BUNDLE_ID)`; one key a book, a hash of its pick key since keys stop at 64 bytes; read at launch, on coming back to the app and on `didChangeExternallyNotification`, written with each send to the other side). iCloud keeps whichever write reached it last, so neither side takes its word: each merges by `WatchBookPlace.supersedes` (latest move wins, a tie to the one further in), writes only places newer than the store's, and writes its own back when the store comes down older, which settles both on the same place. Each side sends the places of the books picked and takes the newer (`WatchBookPlaces`), the iPhone into `AudiobookProgressStore` (its own place kept in the book's history as "Synced from Apple Watch", only for a server it's signed in to), and a book loaded there but paused gives way (`AudiobookPlayer.notePlaceMoved`): moved to the watch's place in the same file, else parked without Plex hearing its old spot (`PlayReporter.forget`), and the server is told the new place (`sendNewerPlace`). On the watch, a paused book's place is never read again off the player (leaving it, a failed file, a load on its way): only playing, a pause and a move keep one, and Play on a book whose newer place is in a part not downloaded yet doesn't play. The watch takes a server's place only when it's clearly newer, by the iPhone's rules (`PlexAudiobook.preferring`). Audiobookshelf's sign-in is lent: the server rotates the refresh token on every renewal, so the iPhone keeps it and the watch, ten minutes before the access token runs out, asks the iPhone for its next (`WatchAccounts.renewTokenIfNeeded`, `sendMessage` with a reply; the iPhone renews first, `credentialsForWatch`), and the files and books it turned away try again (`tokenDidRenew`). The watch tells a book's server the places listening there reached too, with its sends to the iPhone (`WatchBookStore.tellServers`: Audiobookshelf the place, Plex the file's place paused and a finish marked played; places the iPhone or iCloud brought aren't sent back). A book's page has a Sleep Timer while it's loaded (`WatchPlayer.sleepTimer`): 5–60 minutes, or End of Chapter, which pauses as the next chapter starts in the file, or at a file's end loads the next paused at its top

### iPhone downloads
- `DownloadManager` (Plex and Subsonic) runs on a background `URLSession`, but hands it only two downloads at a time (`window`, `admit()`); the rest wait as `.queued` entries with no task. Plex answers requests beyond the couple it's serving with 503, many tasks on the session at once stall each other, and making a task per song for a big playlist froze an iPhone SE for 20 s. Anything that starts or stops downloads goes through `admit()`, not `start()`.
- In the background, a `BGContinuedProcessingTask` (`ContinuedDownloadTask`, the progress card) keeps Cue running so the window goes on as in front. A download tap starts it, and so does Cue becoming active with downloads left over (relaunched part-way). With no card (the system turned it down), Cue in the background hands the session 12 (`suspendedWindow`) so it goes on while Cue is suspended; two at a time waited on the system to wake Cue for each pair, 70–140 s apart. The card expiring (or cancelled from it) pauses what's left, by design.
- A book downloads whole (`download(contentsOf:)` on an `.audiobook`, the book page's `ContainerDownloadButton`): its files as the server keeps them, never converted (`Item.isBookFile`), Audiobookshelf's through a file URL signed as each file starts (its token lasts an hour, so `admit()` renews one about to run out first, read from the token's own `exp`). The player's menu offers Download Book for a book's file, never the file as a song (`LocalDownloadMenuSection`). Keeping a book is Super's (`GatedFeature.bookDownloads`, checked at each Download Book and in `download(contentsOf:)`; one already kept still comes back whole); a book counts as one against the free limit, and its files stay out of the music on this device (`completedSongs`) and out of `DownloadLyrics`. `AudiobookDownloads` keeps the book read whole beside them (Downloads/Books/<container key>.json), which `AudiobookLibrary.load` opens offline or with the server out of reach; an Audiobookshelf book then plays its files without a listening session, and the player doesn't sync the server while offline. Offline, the Audiobooks tab stays while a book is downloaded whole, listing only those. A key can hold `|` (an Audiobookshelf file's `<item>|<index>|<file>`), so a task's description is split at its last `|`.
- Transient failures (408/429/5xx, a dropped connection, "cannot parse response", a conversion cut short) go back in line by themselves, five times, 3 s to 2 min apart (`retryAutomatically`). While Cue is active, tasks taken over from an earlier launch are restarted from their resume data once they run (they barely move otherwise; one waiting for Wi‑Fi is restarted when it starts), and a watchdog restarts any transfer silent for 30 s.
- An album or playlist is listed whole or not at all (`allPlexAlbumSongs`, `allPlexPlaylistSongs`, `PagedList`), so a failed page never leaves a container marked downloaded with songs missing. One the free limit cuts short is still kept, its held-back songs as its missing ones (`removedKeys`, as songs removed from it are), so the Downloads tab lists it with what's here and its page offers Download N More Songs; unkept, its songs were loose and the playlist never showed. Containers are trimmed when a song is removed (`trimContainers`, `removedKeys`), and removing one keeps songs another still holds.
- Plex conversions run as their own clients (`Cue-Download`, `Cue-Download-2`) and in their own transcode session (`cue-download-<ratingKey>`, never the player's `cue-<ratingKey>`): Plex ends a transcode when the same client starts another, and a broken-off conversion looks complete (no Content-Length), so files under half of duration × bitrate are rejected (`DownloadChecks`).
- `DownloadAudit` (Debug) drives downloads from launch arguments on a device, e.g. `xcrun devicectl device process launch --console --terminate-existing --device <udid> dance.cue -- -DownloadAuditReset YES -DownloadPlexPlaylist "❤️ Tracks"`; see the file for the rest. Logs are under the `downloads` category. Pull `Library/Application Support/Downloads/manifest.json` with `devicectl device copy from --domain-type appDataContainer --domain-identifier dance.cue` to check states.
- The Downloads tab (`AppTab.downloads`, `DownloadsTabScreen`, the on-device library of every provider, `OnDeviceLibrary`) shows while there are songs or books here or coming down, or Apple Music downloads, unless switched off in Settings ▸ Appearance (`AppStorageKeys.showDownloadsTab`). Offline it always shows and Browse leaves the tab bar, Downloads leading in its place beside Search (`CueApp.showsBrowseTab`, `fallbackTab`); Radio hides and Audiobooks lists only books downloaded whole. Offline, Search's field reads Search Downloads and searches the on-device library (`OfflineSearchView`), showing the songs downloaded last before anything is typed; `SearchScreen` runs it (`OfflineSearch`), and section titles are rows, not headers, which a plain list pads far below the field. A Debug build reads as offline whatever the network with Settings ▸ Debug ▸ Simulate No Network (or `-dance.cue.simulateOffline YES` at launch), to see all this in the Simulator. Tabs that come and go (Browse, Radio, Audiobooks, Downloads) are left out with an `if`, and the `TabView` is rebuilt when the network comes or goes (`.id(offline.isActive)`): the tab bar matches its items by place, and Browse put back in front came back with the Audiobooks icon. `.hidden(_:)` on these tabs (build 690) kept the icons right; the Radio and Audiobooks freeze blamed on it then was Search's UserDefaults write loop (see **UserDefaults writes** under Key Patterns), so it may be fine, but `if` is what's tested. Settings ▸ Debug ▸ Shrink Tab Bar on Scroll turns off the tab bar's minimize, to compare scrolling, and `notifyutil -p dance.cue.debug.offline` (in the Simulator through `simctl spawn`) flips Simulate No Network. There's no Offline Mode switch any more: `OfflineMode` follows the network alone (`isActive` is no network), and still moves the route to this device. While songs or books come down its icon is a ring round the arrow filling with the run (`DownloadRingIcon`, a template image drawn for each of `runProgressStep`'s twenty steps; the tab bar takes only a plain image from a tab's label), with no badge on the phone; iPad's and the Mac's top bar draws titles only, so there the songs and books still to come are a badge, a book counting once; a Downloading row on top follows the run, and Storage is the toolbar's gear. Storage (`DownloadsScreen`) is one list, no tabs: the room Cue takes (a bar split between songs, books and the playback cache) beside the device's free space (`volumeAvailableCapacityForImportantUsage`, disk space reason 85F4.1 in the root privacy manifest), the free meter, a row each for Downloading, Songs, Albums, Playlists, Books and Apple Music's downloads, each opening a page of its own (`StoragePage`, `RouterDestination.storagePage`; `.bookDownloads` is the Books page), then the settings (cellular, the playback cache, iCloud Drive, the caches). Remove All Songs, Albums, Playlists and Books are in their pages' … menus, Pause, Resume and Cancel All in Downloading's. Artists, Albums and Songs, then Playlists (the playlists downloaded whole, each with its songs here in its order, `ondevice|playlist|<container key>`) and Books (to Storage), with no header, and a Recently Downloaded shelf of albums and playlists, which is its section's header, not a row, so it runs to the screen's edges (a list clips its rows to their section's rounded card). An album, artist or playlist comes off the device from its row on the Albums, Artists or Playlists page (a swipe or a long press, `onDeviceRemoveActions`) or from its page's filled download button (`OnDeviceDownloadButton`), through `OnDeviceLibrary.removeDownloads`: a playlist as one (`removeContainer`), an album or artist song by song, the Files folder's iCloud copies evicted, Apple Music's left to the Music app; the page goes back once its songs are gone. The shelf's tiles have no long-press menu, a list's section header never presenting one. The Albums, Artists and Playlists pages draw their rows as a server's album list does (50 pt covers, 4 pt insets, no separators), and Albums can be a grid of covers by the List / Grid choice every album list shares (`AppStorageKeys.albumsLayout`). It replaced each provider's Downloaded row. The tab bar and the library's lists read `DownloadManager.musicSummary` and `songsHere`, which move only as songs are queued, land or go: `items` changes several times a second while songs come down, and a view reading it is redrawn with every byte. Only the Downloading row reads `items` (`runFraction`); the ring's step moves at most twenty times a run. A downloaded album opens on `MediaDetailView`, filled from the device (`OnDeviceLibrary.isContainer`), each song showing its own track number; an artist on `ArtistDetailView` the same way (`isOnDevice`: their songs and the albums here with a song of theirs, `OnDeviceLibrary.albums(ofArtist:)`, with Play, Shuffle and the filled download button, and no radio or album kinds).

### Apple Watch downloads
- watchOS routes a watch app's `URLSession` traffic through the iPhone whenever the two are connected over Bluetooth (tens of KB/s), and no app can choose otherwise. Low-level networking, `NWPathMonitor` included, is off limits outside audio streaming and VoIP (TN3135), so the app can't ask which way a transfer goes.
- Downloads normally run on a background session (`dance.cue.watch.downloads`), 16 songs handed to it at a time, and carry on with Cue closed. **Fast Download** runs them on a foreground session, four at a time, while Cue is open, and asks for Bluetooth to be turned off in the iPhone's Settings app (Control Center leaves the watch connected), which leaves the watch its own Wi‑Fi. The speed is the evidence of the route (`RouteEstimator`: under 250 KB/s after 5 s is "through iPhone", 400 KB/s or more is Wi‑Fi), and the screen asks again while it's slow. Leaving the app hands what's left back to the background session; returning resumes the fast run. On either session Plex gets two downloads at a time (four of a book's files at once had all but one stall a few hundred KB in until the connection dropped, as on the iPhone) and a book one file at a time, from the file its place is in to the end, then the ones before, the book loaded in the player ahead of everything (`WatchDownloadStore.orderedKeys`): the next chapter is the next to land. When the place moves (played here, the iPhone's, the server's: `bookPlaceDidMove`), a book file under way that isn't the one wanted next makes way, keeping its resume data. A try that brought in 1 MB and can resume from it doesn't use up one of the two retries.
- Each transfer logs its metrics (proxy connection, local and remote address, KB/s) under the `dance.cue.watch` subsystem, for checking the route on a device.
- Only Plex and Subsonic songs, and Plex and Audiobookshelf books, go on the watch: the same rule as `DownloadManager`, since their files are plain URLs. Without Super the free songs (`DownloadManager.freeSongLimit`) are shared with the iPhone and books don't come down: the iPhone sends the watch its share in the context (`WatchAllowance`: the free songs it doesn't hold itself, nil with Super, and whether books may come), the watch sends back what it holds (`WatchHeldDownloads`, its songs on the watch or on their way and its books one each), and the iPhone counts that in `remainingFreeSlots` (`heldAgainstLimit`). The watch never deletes for it: what's here or on its way stays, and the rest of what's picked waits, picked, oldest pick first (`WatchAllowance.admitted`, `WatchDownloadStore.heldBack`, said on Downloads and a book's page) until there's room or Super. Add to Apple Watch on the iPhone checks `GatedFeature.download(of:)` (books Super's). An Audiobookshelf file's key holds bars (`<item>|<index>|<file>`), so a task's description is split at its last `|`, as on the iPhone.
- Songs go at the watch's own quality (`WatchDownloadQuality`: MP3 at 256/192/128 kbps converted by the server, or Original), not the iPhone's Streaming Quality. The watch asks the first time it has music to fetch and keeps it in its defaults; songs come down at the recommended one meanwhile, and closing the question without a choice keeps that (it used to ask again every launch). MP3 because Plex and Subsonic send Opus in Ogg, which the watch's player can't open. Streams are built when a download starts (`WatchSong.stream(at:)`, `ConvertedStream` in MusicSearchKit), so they carry the current sign-ins; a new quality fetches each song again and plays the old file (`previousFileExtension`) until the new one lands.
- Plex converts as it sends, and starting a transcode can end another of the same client, so the watch's run under client ids of their own (`WatchDownloadStore.plexClients`: `Cue-Watch`, `Cue-Watch-2`), never ending one the iPhone is playing, and as many at once as there are ids. One conversion goes about as fast as the server encodes (around 2 MB/s), so two fill more of Wi‑Fi. A conversion the server breaks off (`cannot parse response`, `bad server response`, connection lost) is tried again twice by itself, then counts as failed; opening Cue, new sign-ins or Fast Download try failed songs again. A lookup that fails part-way (a playlist page, one of an artist's albums) fails whole, so a passing fault never deletes songs.
- Beyond the app: **double tap** (and the pinch, watchOS 11+'s `handGestureShortcut(.primaryAction)`) presses Play in the players (the watch's own is the system's; the iPhone's, `PhoneNowPlayingScreen`), a book's page and an album's Play; the home screen has no play button of its own (its bottom bar's play/pause was taken out), so there it does the system's default. No Siri or Shortcuts for now (removed: App Store validation rejects intent descriptions that say "Apple"; they're in git history). `ShuffleDownloadsIntent` (`Watch/Intents`, `isDiscoverable = false`) is an `AudioPlaybackIntent` only for the widget's button and the control, so it plays in the app. **Widgets** (`WatchWidgets/`): one widget for the Smart Stack and faces (rectangular with a Shuffle button, circular, corner, inline; ranked up while playing or downloading) reading `WatchWidgetState`, which `WidgetStatePublisher` writes a few seconds after the store or player changes and then reloads; tapping opens Downloads or Now Playing (`cuewatch://downloads`, `cuewatch://nowplaying`, handled by `onOpenURL`). A Shuffle Downloads control for Control Center on watchOS 26+. The playback intents file is shared with the extension (a membership exception), where `WIDGET_EXTENSION` compiles `perform` empty; the system runs it in the app.
- The watch's home (`LibraryScreen`) has no title: while something's loaded, a Now Playing card at the top whichever library is on show (`NowPlayingCard`: the cover, the song and artist or the book and author, a waveform moving while it plays, on the cover's mesh gradient, `WatchArtworkMesh`, a copy of `ArtworkMeshBackground`'s made from `ArtworkStore`'s cover), opening Now Playing. Opened while something plays (launched, or back from the watch face, not a raised wrist), the app goes straight to that player, the watch's or else the iPhone's once it has answered since opening, within 8 s (`openPlayerIfPlaying`); a widget's link wins. What's loaded outlives the app (`WatchPlayer.restore()`, player.json: the songs, the one playing and its place, or the book), put back paused at launch with nothing in the player until Play. Under the watch's card is the iPhone's, while it has something (`PhoneNowPlaying`); each card carries a glyph of where it plays (the watch, the iPhone, or a speaker, `PlaybackPlace`) rather than a name: while the watch app is open the iPhone sends `PlaybackRoute.presented` as it changes (`WatchSyncService`, `sendMessage` while reachable, a 160 px cover as JPEG, with its clock, a book's chapter and the sleep timer), and the watch asks as it opens. The iPhone also keeps the card, without its cover, in its application context (2 s after each change of song, state or chapter, not the clock; `contextNowPlaying`), so it's on the watch the moment the app opens, before it asks (`apply(contextCard:sentAt:)`: not over a newer answer, nor older than 2 h playing or 10 min paused; it doesn't count as heard for opening the player). The session drops whenever the app leaves the screen (a lowered wrist), so the iPhone counts as out of reach only after 6 s down with the app on screen (`reachGrace`); until then what it last said stands, and requests made meanwhile go once it's back (`PhoneConnection.askPhone`). Play on a watch book with the iPhone in reach asks where (`BookPlayback`, `askingWhereToPlay`: Apple Watch, the iPhone, each speaker it plays to), unless it's the book the watch is in the middle of with the iPhone quiet; the iPhone takes the watch's place sent along and plays it (`WatchSyncMessage.playBookRequest`; on the iPhone itself the route comes back to it, on a speaker it goes there). Albums, playlists, artists and songs ask the same (`PlayChoice`): Play and Shuffle on a server's album or playlist, a swipe on a song row, and Play on what's on the watch; the iPhone reads the pick from its server by the watch's ids and plays the whole list from the song asked for (`playItemRequest`, `WatchSyncService.songs(for:)`). The card then opens a player of its own for the iPhone (`PhoneNowPlayingScreen`, the same `PlayerFace`: Previous/Play/Next, a book's ±15/30 s, each press carried out by the iPhone's player, `WatchPhoneCommand` through `WatchSyncMessage.commandRequest`; a book's chapters top right, `PhoneChaptersScreen`, played with `playChapterRequest`; the sleep timer and a book's speed, `sleepTimerRequest`, `speedRequest`). `-dance.cue.phonePreview YES` with `-dance.cue.watchScreen phone` (or `phoneChapters`, `nowPlaying`) shows it in the simulator with a made-up book (Debug).   `DownloadManager.freeSongLimit` songs held at a time, on the iPhone and the

  `download(contentsOf:)` returns a `BatchResult`), with the meter in
