# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Cue is a multi-platform SwiftUI music player that also controls Sonos speakers. It plays Apple Music, Plex, Subsonic, TuneIn and local files on the device itself (`LocalPlaybackService`) and hands the same queue to a Sonos group (`PlaybackRoute`). It provides native apps for iOS, iPadOS, macOS and tvOS, and includes a menu bar app (Cue Mini). Widgets and Live Activities are switched off for now (see Platform-Specific Features).

## Product Priorities

1. **Best music player first.** Cue is a player that happens to be an excellent Sonos client, not a Sonos remote with a player bolted on. Playback, queue, library, search and Now Playing must be complete on the device alone, with no speaker on the network.
2. **Best Sonos client second.** Everything the device can play must also play on a Sonos group, and the hand-off between the two must be seamless (`PlaybackRoute`).
3. **Every service must play on the device and on Sonos.** A service belongs in Cue only if its audio can be played by the device (MusicKit, a direct stream URL, or a local file) *and* by a speaker. Services whose audio only a speaker can reach are not supported, however popular they are on Sonos. Today that rule excludes Spotify, Tidal, Deezer, SoundCloud, Pandora, Sonos Radio and the speaker's own Music Library. See `Ideas/device-first-services.md` for the audit and the removal plan.

When a change forces a trade-off between the player and the Sonos client, the player wins. Do not add a service, feature or screen that only works when a speaker is present.

## Session Workflow

These rules apply to every session on the Mac (started with `Scripts/claude-remote.sh` and driven from the phone).

### Branch per session
- At the start of every session, before editing anything, create a new branch from the latest `main`: `git fetch origin main && git switch -c claude/<short-topic> origin/main`. Name it after the task, for example `claude/queue-swipe-actions`. If the working tree has uncommitted changes, ask before switching.
- Make every change and commit of the session on that branch. Do not commit to `main`, and do not start another branch in the same session.
- Push the branch with `git push -u origin <branch>` when work is committed. Merge to `main` only when asked.

### Deploy to the iPhone after every build
- When you build the iOS app, run `Scripts/deploy-to-iphone.sh` instead of a simulator build. It builds the `Cue` scheme (Debug) for the connected iPhone, installs it and launches it. The user tests on the phone, so a change is not finished until it has been deployed.
- On failure, it prints the compile errors and writes the full log to `build/device-build.log`. Fix the errors and run it again.
- If it reports that no iPhone is connected, build for the simulator instead (`xcodebuild -project Cue.xcodeproj -scheme Cue -destination 'generic/platform=iOS Simulator' build`) and tell the user the phone was not reachable.
- The script also installs the watch app from the build straight onto the paired Apple Watch (`Scripts/list-watches.py` finds it; `CUE_WATCH=<name or UDID>` picks one, `--no-watch` skips it), so the watch's reason shows in the output when it refuses. The watch has to be known to Xcode (Devices and Simulators) with Developer Mode on.
- Other targets (Mac, TV, Cue Mini) build with `xcodebuild` as usual; only the iOS and watch apps are deployed.

### Logs and crashes from the iPhone
- To check runtime behaviour, deploy with `Scripts/deploy-to-iphone.sh --logs [seconds]` (default 30), or relaunch without rebuilding with `Scripts/iphone-logs.sh [seconds]`. Ask the user to reproduce on the phone while it captures. It shows the last 200 lines; the full capture is in `build/device-console.log`. Set `CUE_LOG_FILTER=<text>` to see only matching lines. `print` and `Logger` output both appear.
- When the user is away from the Mac (on cellular, in the car), run `Scripts/iphone-applog.sh [lines]` once the phone is back in reach. A Debug build keeps its own log in files in its container (`Cue/Debug/PhoneLogFile.swift`: every `dance.cue` message, AVFoundation's errors and the requests that failed inside Cue, written every 20 s, on leaving the foreground and right after a player error, a file a launch, five kept), and the script copies them to `build/phone-logs` with `devicectl`, no password and nothing to do on the phone. A whole device log takes `sudo log collect --device-udid <udid>`, which needs the user at the Mac. A request that fails at once with -1008 and never reaches the server can be a content blocker's URL filter on the phone (Wipr blocked one Plex file URL once).
- When the user says the app crashed, run `Scripts/iphone-crashes.sh` (`--count N` for more) before reading code. It pulls Cue's newest crash report into `build/crashes` and prints the exception, the crash message and the crashed thread with Cue's frames symbolicated. If it says the phone's build doesn't match the local one, deploy again and ask the user to reproduce the crash.
- For crashes in an extension, pass `--process Widgets` (or the extension's executable name).
- For what the car's Now Playing read (CarPlay on iOS 27 sticks to one of Cue's two Now Playing cards), reproduce in the car or Xcode's CarPlay Simulator with the phone on USB, then run `Scripts/carplay-nowplaying-log.sh [15m]`: it collects the phone's system log (`sudo log collect`) into `build/carplay-nowplaying` and shows `mediaremoted`'s lines for `CarPlayTemplateUIHost` and `RemotePlayerService` beside Cue's `localplayback`, `carplay` and `nowplaying` lines.

### Cue (Mac) on this Mac
- `Cue (Mac)` is a Mac Catalyst build of the iOS app (code paths use `targetEnvironment(macCatalyst)`; `os(macOS)` is false there). When working on it, run `Scripts/deploy-to-mac.sh` after building: it builds the scheme (Debug) into `~/Library/Developer/Xcode/DerivedData/Cue-Mac` (`Debug-maccatalyst`), quits any running Cue and launches the new build on this Mac through LaunchServices. Build errors go to `build/mac-build.log`.
- Console: `Scripts/deploy-to-mac.sh --logs [seconds]`, or relaunch without rebuilding with `Scripts/mac-logs.sh [seconds]` (`CUE_LOG_FILTER` works the same). The running app keeps writing to `build/mac-console.log` (a link to `~/Library/Logs/Cue-dev/mac-console.log`).
- Release: prefix any Mac script with `CUE_CONFIGURATION=Release`. A locally built Release has no App Store receipt, so it runs as the free tier.
- Crashes: `Scripts/mac-crashes.sh` (`--count N`, `--process "Cue Mini"`) reads `~/Library/Logs/DiagnosticReports` and symbolicates against the last Mac build.
- Memory: `Scripts/mac-profile.sh [seconds]` relaunches the last Mac build, samples its footprint and its GPU share (default 120 s, every 1 s) while the user reproduces the problem, then captures a memory graph and reports the peak, the biggest jumps with timestamps, leaks, the largest regions (vmmap) and the largest heap types, into `build/profiles/<time>/`. `--stacks` adds allocation call stacks (`MallocStackLogging`), `--attach` profiles the Cue already running, `--trace <template> [seconds]` records an Instruments trace. GPU memory (`footprint`'s "(graphics)" rows) is invisible to `vmmap`, `heap` and the memgraph: a spike in `gpu_mb` alone is offscreen rendering or animation (see Mac GPU cost under Key Patterns), not an allocation leak. Profile the Debug build; Release builds can't be inspected by `leaks`/`heap`. These scripts are Clic's, renamed.

## Architecture

### Core Package Structure
The app is built around several Swift packages in `/Packages`:

1. **SonosKit** - Core Sonos integration and device communication
   - `SonosService` - Main service class managing Sonos system state
   - `SonosAPI` - Network communication with Sonos devices
   - XML parsers for Sonos responses
   - Device discovery and monitoring

2. **MusicSearchKit** - Music service integrations (also linked into the watch app, which browses Plex and Subsonic with it). A dynamic framework: the iOS app gets it embedded through SonosKit, but the watch links it directly, so its target embeds it in its own Embed Frameworks phase
   - Apple Music, Spotify, Plex, Tidal, TuneIn, SoundCloud APIs
   - Authentication services for each platform
   - Search result parsing and models

3. **SubscriptionKit** - In-app purchase management
   - RevenueCat integration for subscriptions

4. **Defaults** - Centralized app settings and storage keys
   - `AppStorageKeys`, `CloudKeys`, `GroupStorageKeys`
   - Feature flags and preferences

5. **Analytics** - Event tracking and analytics
   - User behavior and app usage metrics

6. **VibesDS** - Custom UI design system
   - Reusable SwiftUI components and styles
   - `sidewaysPan(...)`: a drag that only starts sideways (`SidewaysPan`, a `UIPanGestureRecognizer` through `UIGestureRecognizerRepresentable`). It fails at once on a vertical drag and every other pan waits for it, so a volume row in a list or a sheet never takes a scroll or a pull to dismiss (Play On's rows use it)
   - `VibeSlider` (shared with Clic, file for file, as are `SidewaysPan` and `SliderMath`) drags with `SidewaysPan` on iOS, except `immediateDrag` sliders, which begin on touch-down (`TouchDownDrag`) to beat a navigation stack's back swipe. `onLongPress` fires when the slider is held still for half a second, and a held touch then never starts an edit (Clic's volume sliders mute with it). The Mac and visionOS keep the SwiftUI drag. No value animation while a drag is under way, and every division by the range goes through `SliderMath`, so a radio position past a zero duration can't make an infinite fill

7. **WatchSync** - What the iPhone and the watch app share (pure Foundation, tested with `swift test`)
   - `WatchPicks`/`WatchPick` (what's chosen to be on the watch, by id, merged per pick; a pick of a kind or server a side doesn't know is left out, not failed), `WatchBookPlaces` (each book's place, merged per book, the one that moved last winning), `WatchCredentials` (the iPhone's sign-ins; Audiobookshelf's access token lent, never its refresh token), `WatchKeys`, `WatchDownloadQuality`, `WatchSyncMessage` (the application context each side sends, and the watch's request for fresh sign-ins)
   - `TransferRateMeter` and `RouteEstimator`, which tell the watch's own Wi‑Fi from the iPhone relay by speed
   - `WatchWidgetState`, what the watch app leaves in the app group (`group.dance.cue`) for its widgets

### Main App Structure

## Development Guidelines

### Code Organization
- Use `@Observable` for SwiftUI state management
- Services follow singleton pattern with `.shared` instances
- UI components are organized by feature area
- Packages are used for modular, reusable functionality

### Key Patterns
- **Router-based navigation** using `RouterDestination` enums
- **Service injection** through SwiftUI environment
- **CloudStorage** for synced user preferences
- **AppStorage** for local device settings
- **Super** (ported from Clic): `SubscriptionService.apply(_:)` settles it from RevenueCat's customer info (an active entitlement, an active subscription or any one-off purchase) or StoreKit's `Transaction.currentEntitlements` (`StoreKitEntitlements`, the one file that imports StoreKit); either is enough, and of two yeses the longer counts. StoreKit is there because each install's RevenueCat user is anonymous: a device that never restored reads as not subscribed though the account owns Super. RevenueCat is configured only once protected data is available (`whenProtectedDataIsAvailable`, not waited for on the Mac), and Analytics waits with it (`initialize`'s `configured`); `userID` reads empty until then. Each answer goes to `SuperPublisher` (set as `subscriptionUpdated` before `AppBootstrapper.bootstrap`), which writes `Subscription.activeUntil` to the App Group (`UserDefaults.superUntil`, `.distantPast` for no); `bootstrap` resumes from it (`resume(activeUntil:)`) so Super doesn't flash the free tier at launch, and the Shortcuts actions check `GroupStorageKeys.defaults.hasSuper` (this device's date, else the old iCloud flag only Debug and TestFlight builds wrote) and throw `IntentError.superRequired`, which says why. Never publish the launch default: `subscription` is `.notActive` until an answer comes. The paywall closes itself when `isActive` turns on, and `cue://subscribe` opens it only without Super. Tests: `SubscriptionTests` (on an iOS Simulator destination, since SubscriptionKit imports UIKit)
- **One player for both routes**: the player, the mini player and the queue panel draw `PlaybackRoute.presented`, a `PlaybackController` (`Cue/Services/PlaybackController.swift`: `LocalPlaybackService` for this device, `SonosGroupController` for a group, times in seconds on both), not a branch on `route.group`. A route switch changes what the one set of views reads; while a hand-off carries the queue across, `presented` holds on the source (`PlaybackRoute.hold`) until the target is playing the same song with its cover cached, so the player never drops to the speaker's old track mid-switch. Held, `presented` is a `HeldPlaybackController`: the source's song, the hold's playing state and clock (the hand-off keeps it on what's heard through `setHoldClock`), and no commands (`isActive` false, transport no-ops), so views draw a hand-off without special cases; only the queue panel and the player's menus check `route.isHolding` to rest. The hold ends 12 s after the source stops, 30 s at most, and the hand-off's own calls on it are no-ops once a newer switch has cancelled it. The hardware volume follows `route.audibleGroup` (the source until it stops). Speaker-only extras (TV mode, its artwork badges and menu, room volume) read `controller.group`. Queue and drops go to `PlaybackRoute.controller` / `route.group` (the route itself). Song lists mark the song the player shows through `PlaybackRoute.isPresenting(_:)` (the speaker's track, or the row this device's queue is at), read in a small view of its own (`NowPlayingTitle`) so a new song redraws titles, not whole rows. Don't branch a player surface's whole body on the group: a view in two `if` branches is rebuilt on every switch
- **Radio on the device** plays in front of the queue, not in it: `LocalPlaybackService.station` holds the station and `nowPlaying` reads it first, while the queue keeps its songs, its place and the spot in its song (`resumePosition`) behind it, the way a speaker's queue waits while it plays radio. Next Up shows that queue dimmed under "Not Active" with no current row (CarPlay's Up Next says "Not Playing"), and a row tapped or any new Play puts the station away (`arm(at:)`). Stations never become queue rows (`queueable`); a station played at any position plays now (`playStation(_:)`), with `runEnd` at -1 so nothing that edits or tops up the queue reaches its player. It's saved on its own (`LocalStation.json`) and queue positions saved under it are the queue's spot, not the station's time. A station that won't play falls back to what was there (the station before it, or the queue, paused). A live Apple Music station (`.liveRadio`) has no Next; a personal one keeps it (`isPlayingAppleStation`), and Next on one that's stopped starts it
- **Playback progress** is a running clock, not a ticking number: `Room.estimatedPlaybackPosition()` for a speaker, `LocalPlaybackService.progress` for this device. Draw it through VibesDS's `PlaybackTimeline` (redraws once per pixel, only while visible and playing), report positions through `Room.updatePlaybackPosition(_:)` / `noteProgress(_:)` rather than writing them, and move a speaker's position only through `SonosService.seek` / `next` / `previous`, which hold the bar until the speaker lands. Skips are instant and coalesced (`SonosService+TrackSkip.swift`). See `Docs/PlaybackProgress.md`
- **Radio map**: the Radio tab's map tile (`RadioMapTile`, under Local Radio) pushes `RadioMapScreen` (`RouterDestination.radioMap`, zooming out of the tile). The tile is an `MKMapSnapshotter` picture with the pins drawn over it, never a live `Map` (a live map in the list stayed alive under the pushed one, two map views' worth of memory), and the full map is flat (`elevation: .flat`). TuneIn's browse pages carry no place, so `RadioMap.shared` asks each station's `Describe.ashx` (`TuneInAPI.place(for:)`: its `latlon`, else its `location` geocoded with `MKGeocodingRequest`) four at a time and keeps the answers in `Caches/RadioMapPlaces.json`; a station is asked once. Answers reach `places` in one change every 0.5 s (`publish`), not one per station, and the tab's map section is its own view (`RadioMapSection`), so stations landing redraw the tile, not the Radio tab; the pins are `Equatable` and shadow only their frame. Each lookup run logs `placed N of M: … with no place, … without an answer` under the `radioMap` category (many unanswered is TuneIn's 403s, which `place(for:)` backs off from three times). Pins group on a screen-sized grid (`RadioMapCluster`); a pin of one place opens a card of its stations, one spanning places zooms in. Search This Area asks TuneIn's local page for the map's centre (`TuneInBrowsePage.nearby`, `latlon`) and reads as searching until what it found is placed. The bar over the map (`RadioMapStatusBar`) is one glass capsule in an overlay, animated on its own: a top safe-area inset moved the map's centre whenever it changed, and an animation on the whole map flew in the pins that landed with it. No location permission: "near you" is TuneIn's IP-placed local page
- **Lyrics**: `LyricsService.shared` (`Cue/Services/LyricsService.swift`) looks up the song `PlaybackRoute.presented` shows while the player is open (`LyricsRequestModifier`): the song's own service first (Plex lyric streams — asked for rendered with `format=xml`, since a bare request for a LyricFind stream is a 404 —, Subsonic `getLyricsBySongId`/`getLyrics`, a Files `.lrc`/`.txt` sidecar or tags), then LRCLIB (`LRCLibAPI`, behind Settings ▸ Playback ▸ Look Up Lyrics Online, off by default), cached in Caches/Lyrics. The model and parsers are in `MusicSearchKit/Lyrics` (`LyricsTests`). `LyricsView` follows the presented controller's clock; on iPhone lyrics are full screen (`PlayerView.phoneContent`, one layout for cover and lyrics so the cover itself shrinks into the header), elsewhere they take the cover's place. Don't start a lyrics glide alongside anything that resizes the lyrics (the full-screen controls coming back): the resize cuts the glide short. The line being sung fills every frame through a `TextRenderer` drawn over a hidden copy of the line; a renderer that changes every frame on a laid-out `Text` makes SwiftUI measure it and lay out (and scroll-track) everything around it each frame, which on an iPhone SE was two fifths of the main thread. On the Mac the fill is a mask instead (`LyricFill`): a dim and a bright copy of the line, the bright one shown through a bar per row that slides as it's sung, so no text is drawn per frame. Text redrawn every frame runs SwiftUI's GPU renderer on the Mac (~90 MB of GPU memory while a line fills), and the mask costs an iPhone's render server two fifths more than the renderer, so each platform keeps its own. Plex limits LyricFind (a burst of a few requests a second shuts it off for the server for a long while): ask for an agent's lyrics once a song, and pace anything that walks many songs (`DownloadLyrics`: one every 30 s). `LyricsAudit` (Debug, `-LyricsAudit <count>` in the Simulator) checks lookups across the Plex library
- **Audiobooks** (`Cue/Audiobooks/`, one type a file: `Player/` plays a book and draws it in the player, `Views/` its screens and rows, `Data/` the stores, caches and servers; plan in `Ideas/audiobooks.md`): a book is `ContentType.audiobook` (a Plex album from a library chosen as books in the Plex sheet, or tagged with an audiobook genre; an Audiobookshelf item), and its files are ordinary `.track`s. `AudiobookPlayer` plays one from where it was left by replacing the queue with its files (on the device or the route's speaker), follows `PlaybackRoute.presented` every 2 s to keep the place (`AudiobookProgressStore`; the server's reading wins only when over a minute newer, and a Plex reading with no place in a file, only a file counted played, which Cue's own report on leaving it can cause hours later, never moves this device past the file it's in: `PlexAudiobook.preferring`; a Plex finish newer than this device's place wins unless it could be this device's own, past 90% of the last file or dated as it left the book (`AudiobookLibrary.isFinishedElsewhere`). A book file left partway is reported to Plex paused, not stopped (`PlayReporter`), and a place moved with no server to hear it (offline) goes to Plex or Audiobookshelf when the book is next read (`sendNewerPlace`). A file still loading, which reads as its top, and the queue a relaunch leaves parked are never kept as the place, and Play on that parked queue starts from the book's kept place, `resumeOnDevice`. A book file that fails or breaks off, which the queue player would leave for the next file, the next chapter, parks the queue where it stopped and plays from there again a few times, `fileFailed`) and sync the server, and owns speed (device only, `LocalPlaybackService.applyPlaybackRate`), the ±15/30 s skips that replace Previous/Next, the chapters (Previous/Next Chapter; the player's origin line is the chapter, `AudiobookChapterLine`) and End of Chapter, which keeps the player's own sleep timer on the chapter's end. Positions the listener sees are book time (`AudiobookTimeline` maps them to a file and offset). Chapters are each `.m4b`'s marks: Plex's, asked per file (`audiobookChapterMarks`), else read from the file with AVFoundation (`AudiobookChapterReader`), both kept in Caches by the file as it is (`chapterCacheKey`, which changes with the file), so Plex is asked once a file. A book's page shows its last read (`AudiobookReadCache`, else its download's copy) at once and reads the server behind it; a read whose marks didn't come keeps the last read's chapters. Each book keeps a place history beside its place (`AudiobookPlaceHistory`: where it was started, paused, left, and moved away from — a chapter, a scrub, any reading far from where listening would have got, Mark as Finished — and this device's place before another's took over, named for whose it was: the watch's, Plex's or Audiobookshelf's), shown on the Chapters sheet's History page (`AudiobookChaptersView`, a swipe from its chapters) and on the book's page; a tap plays from there. An album page opened on a book or one of its files (the player's title) is the book's page, and an artist page the author's (`AudiobookPlayer.book(containing:)`; `MediaDetailView` and `ArtistDetailView` decide in their bodies, so the page stays the book's while it's the book loaded or last left; `AudiobookAuthorView`): their picture and biography (Plex's artist, Audiobookshelf's author, else Audible's from Audnexus by name, `AudiobookAuthorInfo`, an observed store kept in Caches that the page reads, so it opens whole and a first answer fills in when it lands), the genres Audible files them under, their books partway through, and every book of theirs on Plex (by its album artist) and Audiobookshelf (its author entry, `/api/authors/<id>`; its search matches titles only), oldest first; a book's author line opens it. A book started on this device over music sets the music aside (`LocalPlaybackService.setAsideQueue`, `LocalQueueSetAside.json`: its songs, place, shuffle, repeat and origins); Back to Music (the player's menu, Up Next, Where You Left Off at the top of each music library, Your Music in CarPlay; `AudiobookPlayer.musicSetAside`, on the device route only) plays it again where it was, and Back to Book (`leftBook`) goes the other way. The Audiobooks tab (`AppTab.audiobooks`, `AudiobooksScreen`) leads with one Continue Listening card of the books not finished, newest first, each with its own Play, from the play history and Audiobookshelf's books in progress, then the downloaded books and a row of each server's newest books (Plex's is tried three times as the tab shows, since a listing that fails is no answer rather than a server without books, `PlexAPI.musicLibraries`, then offers Try Again); it shows while Audiobookshelf is signed in or Plex had books when last asked (`AppStorageKeys.hasPlexAudiobooks`, set only by a server with books or a change in the Plex sheet). Audiobookshelf (`AudiobookshelfAPI`, a `DirectStreamProvider`) plays through a listening session whose `/public/session/<id>/track/<n>` URLs a speaker can fetch with no sign-in. Plex keeps a file's `viewOffset` only with "Store track progress" on in the library's settings. Smart Resume (after Overcast's; `SmartResume` in MusicSearchKit): a book played again after a pause goes back a little first, 1 s after a few seconds' pause up to 15 s after a day, never past the start of the chapter it paused in, and not when its place moved while paused (a skip, a chapter, a scrub). It then lands in a pause in the speech near there (`SpeechGaps`, after a minute or more preferring the end of a sentence up to 2 s further back), found in a `LoudnessTrace` of 10 ms windows: on this device an audio tap on each book file's player item (`BookAudioListener`, `MTAudioProcessingTap`, attached in `register`) keeps the last half minute heard, streamed or downloaded alike, with no second fetch; the tap's meter belongs to the tap and goes with the item (the listener holds both weakly). A start from a kept place (Continue Listening, a relaunch) reads the downloaded file around there instead (`LoudnessTrace.reading`, timed in the log), and the watch reads the 20 s before a pause in the background as it pauses (`hearBeforePause`, dropped by `forgetPause` on Play, a move or leaving the book), so Play never waits on a read; a streamed file with nothing heard gets the plain rewind. Each landing logs `smart resume:` under the `audiobooks` category, saying whether it found a pause and how far it moved, and Play on a book's file on this device logs how long it took to play (`logPlayTime`: a seek back on a streamed file may fetch those seconds again). On this device `LocalPlaybackService` stamps when and where a book's file paused (`bookPause`, at the pause and from the poll, so a pause from the AirPods or a call counts) and `smartResume` seeks back, to the frame, before Play; on the watch `WatchPlayer.resume`; a start from a kept place goes back by how long ago it was kept (`updatedAt`). Not on a speaker yet. Tests: `SpeechGapsTests` (pure Swift, runs anywhere)
- **Mac GPU cost**: on the Mac an animated SF Symbol swap or pulse, a `MeshGradient` whose colours change, or an animated swap of the whole player costs ~90 MB of GPU memory for ~2 s each time, and text redrawn through a `TextRenderer` costs the same for as long as it keeps changing, so those are off or replaced there (the lyrics' fill is a sliding mask, `LyricFill`; `GroupMediaControlsView.animatesPlayPause`, `PlaybackIconView`, `VibeGaugeView`) and the player backdrop is a small CPU-drawn bitmap (`ArtworkMeshBackground`)
- **Glass sheet text**: rows on the player's glass sheets (the Chapters sheet's chapters and history, `AudiobookChapterRowLabel`, `AudiobookHistoryList`) dim with opacities of `.primary` (0.8 for a time, 0.6 for a subtitle), not `.secondary` or `.tertiary`, whose vibrancy flickers while the sheet's glass transitions

### Music Service Integration
- All music services implement common protocols in MusicSearchKit
- Authentication flows are handled per-service
- Search results are normalized to `PlayableContent` models

### Sonos Integration
- Sonos is opt-in in the iOS/Mac app: `SonosService.isEnabled` (asked in onboarding by `SonosQuestionStep`; changed later in Settings ▸ Sonos ▸ Use Sonos Speakers; while it is off the Play On button is the system AirPlay picker). While it is off, monitoring and group loads never touch the network, so no Local Network prompt appears. Speakers are only on the local network, so on cellular alone Cue acts as if Sonos were off. `SonosService.isAvailable` (Sonos on, Wi‑Fi or Ethernet, and not in a car) is the one switch: `SonosSystemDiscoverService` reads the path on the main queue and counts losing Wi‑Fi after 5 s (`cellularGrace`, so a moment's drop doesn't), at once on the first path or one read as Cue comes back to the foreground (it may have changed while Cue was suspended); `SonosService` then clears the groups, and looks for them again when Wi‑Fi is back. In a car (CarPlay's screen up or the sound going to CarPlay: `CarConnection`, started at launch and told by `CarPlaySceneDelegate`) `SonosService.isInCar` puts the groups away the same way, and `monitor()` and the group loads stay off the network even on Wi‑Fi, until the car is gone. Everything else derives from `isAvailable` rather than being told: `PlaybackRoute.destination` is the stored choice (`chosen`, mirrored from `PlayDestination.remembered`) or This Device while it is false, `SelectedGroupService.group` is nil while it is false, and the Play On button is the AirPlay picker. Code that means to leave the speakers (Offline Mode, turning Sonos off) compares `route.chosen`, not `destination`, which already reads This Device on cellular. The speaker stays chosen while away, so the route goes back to it on Wi‑Fi, unless this device played meanwhile: `LocalPlaybackService` calls `PlaybackRoute.deviceStartedPlaying()` whenever it starts, which makes This Device the choice while no speaker is in reach. Hide speaker-only UI and route plays behind `sonosService.isAvailable`, keeping `isEnabled` for settings, and make sure a play action never ends in the speaker picker while it is false
- The Play On button (`PlaybackRouteButton`) opens `PlayOnSheet`, a sheet that zooms out of the button (`ZoomTransitionSource.playOn`), laid out like the system AirPlay picker: This Device, then every active room, each row its own volume slider (`VolumeRouteRow`); a muted icon draws a slash on and dims with `.tertiary` (on the glass sheet `.opacity` doesn't dim a white icon, and cut-outs are masks, not `destinationOut` blends). While playback is on this device, or still on its way to a speaker (`PlaybackRoute.isSwitching`), each Sonos group is one row (`GroupRow`: what it's playing or has paused, its volume); once playback lands on a group it opens out into its rooms, animated, and the sheet resizes with it. On a speaker, a bar under the list (`GroupBar`) holds Everywhere (a round toggle: groups every room, or Ungroup All once they all are), All Speakers (the group's volume; a long press mutes them all) and Sync (every room to the group's level). Speaker icons that stand for several rooms carry a badge counting them, in the accent with the count cut out. The volume drag ticks once per percent, from the drag itself (`VolumeHaptics`), and a mute Cue sets holds against the poll for a moment (`Room.holdMute`, `GroupRoom.holdMute`). A sideways drag sets that row's volume (rooms and the group through `SpeakerVolumeWriter`, throttled, holding `isEditingVolume`; while one moves the other follows at once, the group as its rooms' average and the rooms in proportion from where a group drag began, and the speaker's own levels replace the estimates after the hold); a tap (the row is a `Button` with `RouteRowButtonStyle`, for its pressed look, keyboard focus and hover; the whole rectangle takes the touch, hit-tested outside the press scale; `SidewaysPan` cancels its touch when a drag begins) routes there, or on a speaker adds or drops the room (`GroupMembership`, shared with the press-and-hold group menu); a long press mutes one room or plays only there (`GroupMembership.playOnly`). The volume drag is `SidewaysPan`, a UIKit pan that only begins sideways, so vertical drags reach the list and the sheet's pull to dismiss untouched (a SwiftUI drag on the rows took every touch and broke it). Each row is its own view reading its own room, so a level change redraws that row, not the sheet. The header sits above the list and the bar below it, neither in it. The sheet opens at a height fitted to its rooms, the sum of the header, rows, bar and bottom inset each measured with `onGeometryChange` (`refit()`), never from its own current size, which mid-presentation is wrong; it opens at the height it last fitted to for that layout (`AppStorageKeys.playOnSheetHeights`) and can be pulled up to `.large`. The list doesn't scroll while its rows fit (`listFits`); with more rooms than the screen holds it scrolls, its foot fading above the bar. Under the button, the phone's player names where it plays: the group, or on This Device the AirPods, car or AirPlay receiver the audio session routes to (`AudioOutputName`, re-read on each route change; nothing on the built-in speaker), so it's plain that Bluetooth is on

A line-in track's ID is its stream URI (`Track.lineIn(uri:)`, `lineInSourceID`), and `SonosService.getTrack` names the source speaker as its artist, so the player reads "Line In" over "Kitchen"

### Platform-Specific Features
- **iOS**: Focus on mobile-optimized UI. The Lock Screen relies on the system Now Playing card, always on for Cue Super (there is no Lock Screen setting; `NowPlayingSessionService.isPreferenceOn` is fixed to true, and Use iPhone Volume Buttons lives in Settings ▸ Sonos); Live Activities are off for now (`LiveActivityManagerKey` and `LiveActivityManagerFactory` hand out `LiveActivityManagerMock`, `NSSupportsLiveActivities` is unset, and the Widgets extension is not embedded)
- **CarPlay**: `CarPlay/` is an audio-app template scene (Home, Audiobooks, Downloads, Radio; an audio app gets four tabs at most) that always plays on the device and has no Sonos UI: a speaker has no place in a car. Home is Resume and Recently Played over the library; Audiobooks shows while the phone's tab would (`CarPlayLibrary.showsAudiobooks`, put in and taken out with `updateTemplates`): the books partway through as rows with a progress bar, then each server's books as grids. A book plays through `AudiobookPlayer` from where it was left (`CarPlayPlayback.play(book:)`), and Now Playing gives it a `CPNowPlayingPlaybackRateButton` (`bookRates`) in place of shuffle and repeat, and, for a book with chapters, the chapter's place in the book in place of the queue button. It opens Chapters (`fillChapters`): the chapter playing and the ones to come, not those heard (a car can't open a list partway down), each played from its start with `AudiobookPlayer.play(chapter:)`; the one playing has a bar and its time left, set on its row as the book plays (`showChapterProgress`). While CarPlay is connected the phone's app drops Sonos too (`SonosService.isInCar`, see Sonos Integration). Apple Music in the car is left to iOS. MusicKit's player publishes its own Now Playing client from a process of its own, and on iOS 27 the car's Now Playing screen stays on whichever of the app's two clients (Cue's own, MusicKit's) it was on rather than following the one making sound, so during Apple Music it can show a stale or blank card, or a play button while the music plays (FB24840951; https://developer.apple.com/forums/thread/847151). That's Apple's bug and Cue doesn't work around it: publishing Apple Music on Cue's own card and restating it, playing silence to keep Cue awake beside MusicKit, and a paused card for a queue with nothing in a player were all tried and taken out as hacks. The two cards are two MediaRemote clients: Cue's process (`dance.cue(<pid>) > default`) and MusicKit's player in `com.apple.MediaPlayer.RemotePlayerService`. It goes the other way too: a book started after an Apple Music song showed the song, paused, in the car while the book played. So when the stream player takes over from Apple Music, Cue empties MusicKit's stopped queue (`LocalPlaybackService.releaseAppleQueue`), leaving its card nothing stale to show. Between two stream runs (a book to Plex, a book's next file, a song again under Repeat One) Cue's card stays up with its commands while the next run loads (`teardownRun(keepingCard:)`, `finishRun`) and comes down only when nothing plays after: cleared and stopped in between, with its commands gone, the car's Now Playing could let go of it and stay blank for the next song. `LocalNowPlayingPresenter` logs `card up:`, `card kept` and `card down` under `nowplaying`. Under test: iOS 27's MiniPlayer is off in Debug builds (`allowsMiniPlayer`, the template having been reworked with it; release builds keep it), with Settings ▸ Debug ▸ CarPlay MiniPlayer to turn it back on from the next connection, and `Scripts/carplay-nowplaying-log.sh` collects the phone's log (sudo) and shows which card `CarPlayTemplateUIHost` read beside Cue's hand-offs. Next lever if neither moves it: the stream player's card through an `MPNowPlayingSession` (its `AVQueuePlayer`, `becomeActiveIfPossible`). A TuneIn station's card is live (`MPNowPlayingInfoPropertyIsLiveStream`, `update(isLive:)`): the LIVE bar, the station's name on the album line, and play/pause only. iOS draws a live card's pause as a stop button whatever the app does, so `stopCommand` pauses, and skips, scrubbing, shuffle and repeat are switched off, which greys out what can't be hidden; each live publish logs `live card:` under the `nowplaying` category. Apple's reasoning (DTS): a live stream can't be resumed, only rejoined, so a TuneIn station paused for over 30 s (`liveResumeLimit`) starts again live on Play rather than resuming a stream its server has likely dropped. Command states are set only when they change, ahead of the card, and Now Playing's buttons are only sent to the car when they change (`nowPlayingButtons`). Buttons above a list are tiles (`tileRow`: an image row of condensed elements, symbol beside title on a platter, like the Music app's Library buttons), not `headerGridButtons`, which have no platter and on iOS 27 draw only a plain `UIImage(systemName:)` (FB24806621). Home's tiles are a switch: a section (Playlists, Recently Added, Albums) fills the list under them in place. Home's sections (a grid per provider) and Radio are image grids (`imageGrid`: squares with names, 12 at most, the title opening the rest as rows; the playing station's accessory symbol is set by `updatePlayingIndicators`). Rows use `CarPlayArtwork.symbol` and tiles `CarPlayArtwork.tile` so they aren't black on the car's dark screen. Now Playing's shuffle and repeat buttons only take a tap while `changeShuffleModeCommand` / `changeRepeatModeCommand` are enabled with a target (`LocalNowPlayingPresenter` registers them for a stream run, `CarPlayInterface.registerModeCommands` its own while the car is connected so they work during Apple Music too, and the Sonos mirror switches them off for its own card), and the queue button is Cue's own: the system's Up Next button only takes a word or the car's icon, so it's off and a `CPNowPlayingImageButton` shows the song's place in a circle (`CarPlayArtwork.placeButton`: the plain `N.circle` symbol, a list past 50; the phone's ring drawn as a bitmap came out a dot on iOS 27), at zero under a station, which leaves the queue waiting, and opens Up Next. The entitlement is in `Cue/Cue-iOS.entitlements` (iOS SDKs only; `Cue.entitlements` is shared with Mac/TV/Vision and must not carry it), the scene is in `Cue/Info.plist`, and `AppDelegate.application(_:configurationForConnecting:)` hands that role `CarPlaySceneDelegate`. Test it in the Simulator with I/O ▸ External Displays ▸ CarPlay
- **macOS**: Leverage menu bar app and Mac-specific controls
- **tvOS**: Optimize for remote control navigation
- **watchOS**: A device-first player for Plex and Subsonic, rewritten from scratch (the old Sonos remote and its widgets live in git history). The watch is the client: it browses and searches the servers itself with MusicSearchKit (its home screen, `WatchLibraryBrowser`, `WatchAccounts`), with the sign-ins the iPhone shares (`WatchCredentials`). What's on the watch is a list of picks — albums, playlists, artists and songs by id (`WatchPicks`) — made on either device: browsing on the watch, Add to Apple Watch in a menu on the iPhone (Settings ▸ Storage ▸ Apple Watch lists them). Only the picks cross, as each side's application context (the iPhone's also carries the sign-ins); each side merges what arrives per pick (later of add and removal wins, removals kept as tombstones) and sends back only when the other was missing something. The watch looks each pick up on its server (`WatchLibraryBrowser.songs(for:)`), again when the sign-ins change and every six hours, and `WatchDownloadStore` downloads the songs; `WatchPlayer` plays the files through a long-form audio session (`UIBackgroundModes: audio` — watchOS ignores `WKBackgroundModes` for audio). **Books** are picks too (`WatchPick.Kind.audiobook`: a Plex album in a library kept for books, the iPhone's choice of libraries crossing with the Plex sign-in, or an Audiobookshelf item), added from the watch's Audiobooks shelves (Continue Listening, Plex Books, Audiobookshelf; `WatchBookShelf`, `BrowseBookScreen`) or Add to Apple Watch in a book's menu and page on the iPhone. `WatchLibraryBrowser.book(for:)` reads a book's files, chapters (Plex's marks, Audiobookshelf's, else the downloaded files' own with AVFoundation, `readChaptersIfNeeded`) and the server's place; its files come down as the server keeps them, whatever the quality, and stay out of the music (counts, Shuffle Downloads). `WatchPlayer.playBook` plays one from its place (`WatchBookStore`), at its own speed, with ±15/30 s skips for Previous/Next, keeps the place every 5 s and on a pause, and stops at a file not downloaded yet rather than skip it; `BookScreen` is its page. Now Playing shows a book as Apple Books does: the chapter over the book's title, the time into the chapter against its length, and the chapter number, moved on the moment the next chapter starts (a boundary time observer at its start in the file playing). The app's Now Playing (`NowPlayingScreen`) is the system's `NowPlayingView`, kept for the Digital Crown's volume and the route picker, with a button top right to the book's page while a book plays. Places cross with the picks, and through iCloud's key-value store for when the two are out of reach (`CloudBookPlaces`: both apps name the iPhone app's store, `$(TeamIdentifierPrefix)$(BUNDLE_ID)`; one key a book, a hash of its pick key since keys stop at 64 bytes; read at launch, on coming back to the app and on `didChangeExternallyNotification`, written with each send to the other side). iCloud keeps whichever write reached it last, so neither side takes its word: each merges by `WatchBookPlace.supersedes` (latest move wins, a tie to the one further in), writes only places newer than the store's, and writes its own back when the store comes down older, which settles both on the same place. Each side sends the places of the books picked and takes the newer (`WatchBookPlaces`), the iPhone into `AudiobookProgressStore` (its own place kept in the book's history as "Before Apple Watch's place", only for a server it's signed in to), and a book loaded there but paused gives way (`AudiobookPlayer.notePlaceMoved`): moved to the watch's place in the same file, else parked without Plex hearing its old spot (`PlayReporter.forget`), and the server is told the new place (`sendNewerPlace`). On the watch, a paused book's place is never read again off the player (leaving it, a failed file, a load on its way): only playing, a pause and a move keep one, and Play on a book whose newer place is in a part not downloaded yet doesn't play. The watch takes a server's place only when it's clearly newer, by the iPhone's rules (`PlexAudiobook.preferring`). Audiobookshelf's sign-in is lent: the server rotates the refresh token on every renewal, so the iPhone keeps it and the watch, ten minutes before the access token runs out, asks the iPhone for its next (`WatchAccounts.renewTokenIfNeeded`, `sendMessage` with a reply; the iPhone renews first, `credentialsForWatch`), and the files and books it turned away try again (`tokenDidRenew`)

### iPhone downloads
- `DownloadManager` (Plex and Subsonic) runs on a background `URLSession`, but hands it only two downloads at a time (`window`, `admit()`); the rest wait as `.queued` entries with no task. Plex answers requests beyond the couple it's serving with 503, many tasks on the session at once stall each other, and making a task per song for a big playlist froze an iPhone SE for 20 s. Anything that starts or stops downloads goes through `admit()`, not `start()`.
- In the background, a `BGContinuedProcessingTask` (`ContinuedDownloadTask`, the progress card) keeps Cue running so the window goes on as in front. A download tap starts it, and so does Cue becoming active with downloads left over (relaunched part-way). With no card (the system turned it down), Cue in the background hands the session 12 (`suspendedWindow`) so it goes on while Cue is suspended; two at a time waited on the system to wake Cue for each pair, 70–140 s apart. The card expiring (or cancelled from it) pauses what's left, by design.
- A book downloads whole (`download(contentsOf:)` on an `.audiobook`, the book page's `ContainerDownloadButton`): its files as the server keeps them, never converted (`Item.isBookFile`), Audiobookshelf's through a file URL signed as each file starts (its token lasts an hour, so `admit()` renews one about to run out first, read from the token's own `exp`). The player's menu offers Download Book for a book's file, never the file as a song (`LocalDownloadMenuSection`). A book counts as one against the free limit, and its files stay out of the music on this device (`completedSongs`) and out of `DownloadLyrics`. `AudiobookDownloads` keeps the book read whole beside them (Downloads/Books/<container key>.json), which `AudiobookLibrary.load` opens offline or with the server out of reach; an Audiobookshelf book then plays its files without a listening session, and the player doesn't sync the server while Offline Mode is on. Offline, the Audiobooks tab stays while a book is downloaded whole, listing only those. A key can hold `|` (an Audiobookshelf file's `<item>|<index>|<file>`), so a task's description is split at its last `|`.
- Transient failures (408/429/5xx, a dropped connection, "cannot parse response", a conversion cut short) go back in line by themselves, five times, 3 s to 2 min apart (`retryAutomatically`). While Cue is active, tasks taken over from an earlier launch are restarted from their resume data once they run (they barely move otherwise; one waiting for Wi‑Fi is restarted when it starts), and a watchdog restarts any transfer silent for 30 s.
- An album or playlist is listed whole or not at all (`allPlexAlbumSongs`, `allPlexPlaylistSongs`, `PagedList`), so a failed page never leaves a container marked downloaded with songs missing. Containers are trimmed when a song is removed (`trimContainers`, `removedKeys`), and removing one keeps songs another still holds.
- Plex conversions run as their own clients (`Cue-Download`, `Cue-Download-2`) and in their own transcode session (`cue-download-<ratingKey>`, never the player's `cue-<ratingKey>`): Plex ends a transcode when the same client starts another, and a broken-off conversion looks complete (no Content-Length), so files under half of duration × bitrate are rejected (`DownloadChecks`).
- `DownloadAudit` (Debug) drives downloads from launch arguments on a device, e.g. `xcrun devicectl device process launch --console --terminate-existing --device <udid> dance.cue -- -DownloadAuditReset YES -DownloadPlexPlaylist "❤️ Tracks"`; see the file for the rest. Logs are under the `downloads` category. Pull `Library/Application Support/Downloads/manifest.json` with `devicectl device copy from --domain-type appDataContainer --domain-identifier dance.cue` to check states.

### Apple Watch downloads
- watchOS routes a watch app's `URLSession` traffic through the iPhone whenever the two are connected over Bluetooth (tens of KB/s), and no app can choose otherwise. Low-level networking, `NWPathMonitor` included, is off limits outside audio streaming and VoIP (TN3135), so the app can't ask which way a transfer goes.
- Downloads normally run on a background session (`dance.cue.watch.downloads`), 16 songs handed to it at a time, and carry on with Cue closed. **Fast Download** runs them on a foreground session, four at a time, while Cue is open, and asks for Bluetooth to be turned off in the iPhone's Settings app (Control Center leaves the watch connected), which leaves the watch its own Wi‑Fi. The speed is the evidence of the route (`RouteEstimator`: under 250 KB/s after 5 s is "through iPhone", 400 KB/s or more is Wi‑Fi), and the screen asks again while it's slow. Leaving the app hands what's left back to the background session; returning resumes the fast run. On either session Plex gets two downloads at a time (four of a book's files at once had all but one stall a few hundred KB in until the connection dropped, as on the iPhone) and a book one file at a time, from the file its place is in to the end, then the ones before, the book loaded in the player ahead of everything (`WatchDownloadStore.orderedKeys`): the next chapter is the next to land. When the place moves (played here, the iPhone's, the server's: `bookPlaceDidMove`), a book file under way that isn't the one wanted next makes way, keeping its resume data. A try that brought in 1 MB and can resume from it doesn't use up one of the two retries.
- Each transfer logs its metrics (proxy connection, local and remote address, KB/s) under the `dance.cue.watch` subsystem, for checking the route on a device.
- Only Plex and Subsonic songs, and Plex and Audiobookshelf books, go on the watch: the same rule as `DownloadManager`, since their files are plain URLs. Adding is gated by `FeatureGate` `.downloads`, with no separate limit. An Audiobookshelf file's key holds bars (`<item>|<index>|<file>`), so a task's description is split at its last `|`, as on the iPhone.
- Songs go at the watch's own quality (`WatchDownloadQuality`: MP3 at 256/192/128 kbps converted by the server, or Original), not the iPhone's Streaming Quality. The watch asks the first time it has music to fetch and keeps it in its defaults; songs come down at the recommended one meanwhile, and closing the question without a choice keeps that (it used to ask again every launch). MP3 because Plex and Subsonic send Opus in Ogg, which the watch's player can't open. Streams are built when a download starts (`WatchSong.stream(at:)`, `ConvertedStream` in MusicSearchKit), so they carry the current sign-ins; a new quality fetches each song again and plays the old file (`previousFileExtension`) until the new one lands.
- Plex converts as it sends, and starting a transcode can end another of the same client, so the watch's run under client ids of their own (`WatchDownloadStore.plexClients`: `Cue-Watch`, `Cue-Watch-2`), never ending one the iPhone is playing, and as many at once as there are ids. One conversion goes about as fast as the server encodes (around 2 MB/s), so two fill more of Wi‑Fi. A conversion the server breaks off (`cannot parse response`, `bad server response`, connection lost) is tried again twice by itself, then counts as failed; opening Cue, new sign-ins or Fast Download try failed songs again. A lookup that fails part-way (a playlist page, one of an artist's albums) fails whole, so a passing fault never deletes songs.
- Beyond the app: **double tap** (and the pinch, watchOS 11+'s `handGestureShortcut(.primaryAction)`) presses Play in the players (the watch's own is the system's; the iPhone's, `PhoneNowPlayingScreen`), a book's page and an album's Play; the home screen has no play button of its own (its bottom bar's play/pause was taken out), so there it does the system's default. No Siri or Shortcuts for now (removed: App Store validation rejects intent descriptions that say "Apple"; they're in git history). `ShuffleDownloadsIntent` (`Watch/Intents`, `isDiscoverable = false`) is an `AudioPlaybackIntent` only for the widget's button and the control, so it plays in the app. **Widgets** (`WatchWidgets/`): one widget for the Smart Stack and faces (rectangular with a Shuffle button, circular, corner, inline; ranked up while playing or downloading) reading `WatchWidgetState`, which `WidgetStatePublisher` writes a few seconds after the store or player changes and then reloads; tapping opens Downloads or Now Playing (`cuewatch://downloads`, `cuewatch://nowplaying`, handled by `onOpenURL`). A Shuffle Downloads control for Control Center on watchOS 26+. The playback intents file is shared with the extension (a membership exception), where `WIDGET_EXTENSION` compiles `perform` empty; the system runs it in the app.
- The watch's home (`LibraryScreen`) has no title: while something's loaded, a Now Playing card at the top whichever library is on show (`NowPlayingCard`: the cover, the song and artist or the book and author, a waveform moving while it plays, on the cover's mesh gradient, `WatchArtworkMesh`, a copy of `ArtworkMeshBackground`'s made from `ArtworkStore`'s cover), opening Now Playing. What's loaded outlives the app (`WatchPlayer.restore()`, player.json: the songs, the one playing and its place, or the book), put back paused at launch with nothing in the player until Play. While the watch has nothing playing, the card is the iPhone's (`PhoneNowPlaying`, with where it plays: the iPhone or a Sonos group): while the watch app is open the iPhone sends `PlaybackRoute.presented` as it changes (`WatchSyncService`, `sendMessage` while reachable, a 160 px cover as JPEG), and the watch asks as it opens. The card then opens a player of its own for the iPhone (`PhoneNowPlayingScreen`: the cover, the song, Previous/Play/Next, a book's ±15/30 s, each press carried out by the iPhone's player, `WatchPhoneCommand` through `WatchSyncMessage.commandRequest`), never the system's `NowPlayingView`, which picks its source itself and with a book loaded on the watch showed the watch's book. Music from a queue has Up Next top right (`PhoneQueueScreen`, shown while `WatchPhoneNowPlaying.queueCount` is above zero and it isn't a book): the iPhone answers `queueRequest` with its queue from the song playing on, 50 songs at most (`WatchPhoneQueue`: this device's `LocalPlaybackService.queue`, or that stretch of a Sonos group's read with `getQueue(ip:with:total:)`; no current song and dimmed under "Not Active" while a station plays in front of it or the speaker is on radio), asked again whenever the queue's place or length changes (`queuePosition`, `queueCount` in what plays); a tap plays that song there (`playQueueRequest`: `LocalPlaybackService.play(at:)` or `SonosService.seek(trackNumber:on:)`, not during a hand-off) and goes back to the player. With the iPhone out of reach (`PhoneNowPlaying.isPhoneInReach`, WatchConnectivity's `isReachable`, taken as in reach until the session says), an On This Watch section leads instead, Downloads and the book banner, and the library's section goes without them; then the library chosen with the picker top right (an icon; `HomeLibrary`, kept under `librarySource`), its section led by a Downloads row (the count of songs and books on the watch in its title) opening `DownloadsScreen` (Fast Download while songs are still to come, then what's on the watch, each with the room it takes): Plex or Subsonic shows its lists (playlists, recently added, albums, artists, songs — the same as the iPhone's library screens) under its name with a Search row last (`TextFieldLink`), and Audiobooks, offered while there are books on the watch or a server with them, led by the three books on the watch last listened to and not finished (the latest a banner on its cover's gradient that plays it, `BookBanner`, the two before it as tiles, `BookTile`), then the other books on the watch with what's left of each and the servers' shelves. Settings is top left (quality, storage, Remove All, which sign-ins arrived, the version and build). No bottom bar: play and pause are in the player the card opens. Screens zoom out of the row or button that opened them (watchOS 11 `navigationTransition(.zoom)`): the routes are the ids, and the home screen's namespace reaches rows further in through `\.zoomNamespace`. The player hands Now Playing the song's cover (`ArtworkStore`, prefetched when a pick is looked up, so it shows offline); a Plex song without its own cover uses its album's (`parentThumb`). A song goes on with a tap, an album or playlist opens on its songs to add whole or one at a time, an artist on its albums. 40 rows a page, with no iPhone in reach. Keys match the iPhone's download manager (`WatchKeys`), so a pick made on either device is the same pick. MusicKit has no player on watchOS (`ApplicationMusicPlayer` and `SystemMusicPlayer` aren't available there), so Apple Music stays out.

  catalog track ID in `content.id` (for Apple, the numeric `song:<ID>`), so
  previews can be enriched by ID without re-fetching tracks.
- Approach used: `MusicSearchService.enrichWithPreviews([PlayableContent])` —
  batch `MusicCatalogResourceRequest<Song>` keyed off `content.id`, chunked at
  100 to respect the API id cap; call it after each `getQueue` in
  `QueueScreen.scrollToNowPlaying` and `UpNextContentView.loadUpNext` /
  `loadMoreTracks` (`MusicSearchService.shared` is already in the environment
  via `.withEnvironments()`).
- UI parity lives in `QueueCellView` (own cell, not the shared
  `PlayableContentView`): progress-fill background, tap-to-stop on the cell,
  stable disabled-Menu + overlay stop icon, leading swipe Preview action,
  `contextMenu(preview:)` with `SongPreviewCard`, and `SongPreviewButton` in
  the ellipsis menu.
- Scope decided: Apple Music only first (Spotify/Deezer would each need their
  own preview-URL lookup path).

### Monetization notes
- Downloads (Plex/Subsonic, `DownloadManager`) are free up to
  `DownloadManager.freeSongLimit` songs held at a time; Cue Super lifts the
  cap. The gate lives in the manager (`download(_:)` returns `false`,
  `download(contentsOf:)` returns a `BatchResult`), with the meter in
  `DownloadsScreen` and the "This Device" menu.
- Super Day (a free 24-hour pass to Super, once a month) is designed but not
  built — see `Ideas/super-day.md`. It needs the `SubscriptionService`
  activity check moved to `entitlements.active` first.
